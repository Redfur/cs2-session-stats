# demo-ingestion Specification

## Purpose

Принимает файлы демок CS2, загруженные пользователем вручную, сохраняет их и обрабатывает асинхронно, чтобы из них можно было получить статистику матча.

## Requirements

### Requirement: Загрузка демок в сессию
Система SHALL принимать одну или несколько демок за один запрос в рамках существующей сессии. Для каждого файла создаётся матч в статусе `pending`, ответ содержит результат по каждому файлу отдельно.

#### Scenario: Загрузка нескольких демок
- **WHEN** пользователь загружает в сессию три корректных файла `.dem`
- **THEN** создаются три матча в статусе `pending`, ответ содержит идентификатор матча для каждого файла

#### Scenario: Загрузка в несуществующую сессию
- **WHEN** указан неизвестный идентификатор сессии
- **THEN** система отклоняет запрос с ошибкой «не найдено» и не сохраняет файлы

#### Scenario: Частичный успех
- **WHEN** из двух файлов один корректный, а второй имеет неподдерживаемое расширение
- **THEN** корректный файл принимается, для второго в ответе указана ошибка

### Requirement: Поддерживаемые форматы
Система SHALL принимать файлы `.dem`, а также сжатые `.dem.gz`, `.dem.bz2`, `.dem.zst` и `.zip`, содержащий ровно один `.dem`. Сжатые файлы распаковываются перед обработкой.

#### Scenario: Сжатая демка
- **WHEN** загружен файл `match.dem.zst`
- **THEN** система распаковывает его и обрабатывает как обычную демку

#### Scenario: Zip с несколькими демками
- **WHEN** загружен `.zip`, содержащий два `.dem`
- **THEN** файл отклоняется с ошибкой о том, что архив должен содержать ровно одну демку

#### Scenario: Неподдерживаемое расширение
- **WHEN** загружен файл `notes.txt`
- **THEN** файл отклоняется с ошибкой о неподдерживаемом формате

### Requirement: Ограничение размера
Система SHALL отклонять файлы, распакованный размер которых превышает настраиваемый лимит (по умолчанию 1 ГБ).

#### Scenario: Слишком большой файл
- **WHEN** распакованная демка превышает лимит
- **THEN** файл отклоняется с ошибкой о превышении размера, частично записанные данные удаляются

### Requirement: Дедупликация
Система MUST определять дубликаты по SHA-256 распакованного содержимого демки. Повторная загрузка уже известной демки не создаёт новый матч, а возвращает ссылку на существующий матч и его сессию. Демка удалённого матча дубликатом не считается.

#### Scenario: Повторная загрузка той же демки
- **WHEN** пользователь загружает демку, которая уже есть в системе (в этой или другой сессии)
- **THEN** новый матч не создаётся, в ответе для файла указан статус `duplicate` и идентификаторы существующего матча и сессии

#### Scenario: Та же демка в другом архиве
- **WHEN** одна и та же демка загружена сначала как `.dem`, затем как `.dem.gz`
- **THEN** вторая загрузка распознаётся как дубликат

#### Scenario: Повторная загрузка после удаления
- **WHEN** матч удалён (сам или вместе с сессией), и пользователь снова загружает ту же демку
- **THEN** демка принимается как новая, создаётся новый матч в статусе `pending`

### Requirement: Хранение исходных демок
Система SHALL сохранять распакованную демку на диске для каждого принятого матча, чтобы её можно было обработать повторно. Файл демки хранится, пока существует её матч, и удаляется вместе с матчем или его сессией.

#### Scenario: Файл сохранён
- **WHEN** демка принята
- **THEN** её содержимое доступно на диске сервиса, пока существует матч

#### Scenario: Файл удалён вместе с матчем
- **WHEN** матч удалён (сам или вместе с сессией)
- **THEN** файл его демки удаляется с диска сервиса

#### Scenario: Ошибка удаления файла
- **WHEN** матч удалён, а файл демки удалить не удалось
- **THEN** удаление матча всё равно считается выполненным, ошибка записывается в журнал сервиса

### Requirement: Асинхронная обработка и статусы
Система SHALL обрабатывать демки в фоне, не блокируя ответ на загрузку. Каждый матч проходит статусы `pending` → `parsing` → `done` или `failed`. Для `failed` сохраняется текст ошибки.

#### Scenario: Успешная обработка
- **WHEN** загружена корректная демка
- **THEN** ответ на загрузку приходит до окончания парсинга, а матч через некоторое время переходит в `done`

#### Scenario: Повреждённая демка
- **WHEN** загружен файл с расширением `.dem`, который не является корректной демкой CS2
- **THEN** матч переходит в `failed`, пользователь видит текст ошибки

#### Scenario: Перезапуск сервиса
- **WHEN** сервис перезапущен, пока матчи были в статусе `pending` или `parsing`
- **THEN** после старта эти матчи снова ставятся в обработку

### Requirement: Выбор демок в интерфейсе
Интерфейс SHALL принимать демки перетаскиванием файлов в зону загрузки на странице сессии и через выбор файлов (зона доступна с клавиатуры). Файлы с расширением не из списка поддерживаемых форматов MUST отсеиваться до отправки с сообщением, какие файлы пропущены и какие форматы поддерживаются.

#### Scenario: Перетаскивание нескольких файлов
- **WHEN** пользователь перетаскивает в зону три файла `.dem`
- **THEN** все три встают в очередь загрузки в том же порядке с будущими номерами матчей

#### Scenario: Неподдерживаемый файл
- **WHEN** среди перетащенных файлов есть `match.rar`
- **THEN** `match.rar` не попадает в очередь, под зоной показано, что он пропущен, и перечислены форматы `.dem`, `.dem.gz`, `.dem.bz2`, `.dem.zst`, `.zip`

### Requirement: Последовательная загрузка с прогрессом
Интерфейс SHALL отправлять файлы очереди по одному, в порядке очереди, каждый отдельным запросом, поэтому порядок матчей совпадает с порядком файлов. Для каждого файла показываются процент, отправленный и полный объём и оценка оставшегося времени. После отправки у файла показывается результат: принят (со ссылкой на матч), уже загружен или ошибка с текстом.

#### Scenario: Порядок матчей при загрузке очередью
- **WHEN** в сессию с двумя матчами загружается очередь из файлов A, B
- **THEN** A получает номер 3, B — номер 4

#### Scenario: Прогресс файла
- **WHEN** у файла 690 МБ отправлено 414 МБ
- **THEN** у файла показано 60% и «414 из 690 МБ» с оценкой оставшегося времени

#### Scenario: Ошибка одного файла
- **WHEN** сервер отклонил второй файл очереди как архив с двумя демками
- **THEN** у второго файла показана ошибка сервера, а загрузка остальных файлов продолжается

### Requirement: Отмена загрузки
Интерфейс SHALL позволять отменить отправку отдельного файла и всю оставшуюся очередь. Отменённый файл MUST NOT становиться матчем. Файлы, уже принятые сервером, отмена не затрагивает.

#### Scenario: Отмена текущего файла
- **WHEN** пользователь отменяет файл, который отправляется
- **THEN** отправка прерывается, матч из него не создаётся, загрузка переходит к следующему файлу

#### Scenario: Отмена очереди
- **WHEN** в очереди три файла, первый уже принят, второй отправляется, и пользователь отменяет всю очередь
- **THEN** первый файл остаётся матчем, второй и третий не загружаются
