# Design

## Context

- OVR (`internal/rating`, архив `2026-10-14-add-player-rating`) — EMA значения матча, сейчас это `Counters.Rating()` (Rating 2.0). Оценки за матч и сессию считаются там же (`stats.ScorePoints`). Все производные считаются при чтении.
- В базе уже есть хронология убийств `match_kills`: время, убийца, жертва, ассистент, флеш-ассист, размен. Есть раунды `match_rounds`: победитель, сторона команды A, время начала и конца, восстановленный раунд. Команды игроков лежат в `match_players.team`.
- Нет снаряжения игроков и времени установки бомбы: `parser.BombEvent` хранит только действие и игрока, `ComputeExt` пишет в `match_player_ext` только счётчики установок.
- HLTV не публикует ни формулу Rating 3.0, ни таблицу шансов. Известны принципы и опорные числа из [Introducing Rating 3.0](https://www.hltv.org/news/42485/introducing-rating-30): двойное входное убийство за T — 48% → 89%; открывающее убийство — около +20%; победа в 1v1 — около +50%; против полного эко шанс около 96%; Round Swing в сумме по раунду равен нулю; сохранившие оружие наказываются как проигравшие клатч. После обновления в октябре 2025 вес Round Swing — около 33%.
- Матчей мало (17 матчей, 390 раундов, 2 803 убийства), поэтому подбирать параметры по ним нельзя (решение пользователя).

## Goals / Non-Goals

**Goals:**
- Значение матча — одна функция в `internal/rating`, чтобы позже менять формулу в одном месте.
- Round Swing считается при чтении: правка модели шанса не требует повторного разбора демок.
- Повторный разбор нужен один раз — чтобы сохранить снаряжение и время установки бомбы.

**Non-Goals:**
- Поправка убийств, урона и выживания по категориям оружия (eco-adjust Rating 3.0). Экономика входит только через шанс раунда.
- Зависимость шанса от времени раунда и от карты; деление заслуги по доле урона (урон по жертве в базе не хранится).
- Мульти-киллы как отдельный бонус и разложение изменения OVR.

## Decisions

### 1. Модель шанса выиграть раунд

Шанс стороны T при раскладе:

```
logit P_T = b0 + kA·(nT − nCT)/(nT + nCT) + bPlant·planted + bEq·clamp(ln(eqT / eqCT), −2.5, 2.5)
b0 = logit(0.48) = −0.08,  kA = 8,  bPlant = 1.0,  bEq = 1.8
P_CT = 1 − P_T;  при nT = 0 или nCT = 0 исход раунда уже определён
```

- Доля перевеса `(nT − nCT)/(nT + nCT)` делает лишнего игрока важнее при малом числе живых. Проверка по опорным числам при равной закупке: 5v5 → 48%, 5v4 → 69% (+21, HLTV около +20), 5v3 → 87% (HLTV 89%), 1v1 → 48% (победа в клатче около +50), 4v1 → 99.1% (добивание даёт меньше 1 п.п.).
- `bEq` подобран так, чтобы полная закупка (около 23 500 $ на команду) против полного эко (около 4 000 $) давала около 96%: ln(5.9) ≈ 1.77, 1.77 · 1.8 ≈ 3.2 логита.
- `bPlant = 1.0` — допущение: после установки при равном раскладе T выигрывает около 71%. Публичного числа HLTV для этого нет, константа записана как допущение и уточняется вместе с 1.3.
- Если снаряжение неизвестно (0 у любой из команд), соотношение считается равным.
- Альтернативы: таблица по раскладам живых — нет публичного источника; модель по нашим раундам — пользователь отказался.

### 2. Распределение Round Swing (`rating.RoundSwing`)

Раунд проигрывается по убийствам в порядке времени. Начальный расклад — число игроков каждой команды в матче (по `match_players`, не больше 5). Бомба считается установленной для убийств после `plant_ms`.

- **Убийство соперника:** Δ = P(команды убийцы после) − P(до). Убийце — `Δ`, при ассисте или флеш-ассисте — `0.75·Δ` убийце и `0.25·Δ` ассистенту. Жертве — `−Δ`.
- **Убийство союзника**: Δ отрицательная для команды убийцы, вся ложится на убийцу, жертве 0.
- **Смерть от мира или самоубийство:** жертве `−Δ`.
- **Конец раунда:** победителям остаток `1 − P(победителей)` делится пропорционально их положительному вкладу в раунде, а без вклада — поровну между живыми (если живых нет, между всеми). Проигравшим `−P(проигравших)` делится поровну между живыми — так наказываются сохранившие оружие (если живых нет, между всеми). Сумма по раунду — ноль.
- Восстановленный раунд и раунд без хронологии в Round Swing не входят. Знаменатель — `match_player_ext.rounds`.

### 3. Значение матча (`rating.MatchValue`)

```
swingRating = 1 + swing / 0.03          // swing — Round Swing за раунд в долях; ±3% за раунд → 2.0 / 0.0
value       = 0.67·Rating20 + 0.33·swingRating
```

- Вес 0.33 — вес Round Swing в Rating 3.0 после обновления HLTV. Масштаб 0.03 выбран так, чтобы разброс `swingRating` был сопоставим с Rating 2.0 (у HLTV лучшие игроки года — около +3.8% за раунд).
- Round Swing в среднем по компании — ноль, поэтому среднее значение близко к среднему Rating 2.0.
- Матч без данных (`result_version < store.SwingSinceVersion`) → `value = Rating20`.
- Значение нескольких матчей (сессия, «Среднее за 20») — среднее значений матчей, взвешенное по раундам. Сумма счётчиков для этого больше не используется: значение нелинейно по сумме из-за матчей без данных.

### 4. Данные

- **Парсер:** на `RoundFreezetimeEnd` для каждого игрока берётся `EquipmentValueFreezeTimeEnd()`, суммы по командам → `Round.EquipA`, `Round.EquipB`. В `BombEvent` добавляется `Time` (`CurrentTime()`). Время установки — первое событие `planted` раунда.
- **Миграция 006:** `match_rounds` + `equip_a`, `equip_b`, `plant_ms` (INTEGER NOT NULL DEFAULT 0). У существующих строк 0 — данных нет, это отличает их `result_version`.
- **`store.SwingSinceVersion = 4`**, `worker.ProcessingVersion` 3 → 4: при старте все матчи встают на пересчёт; ошибка пересчёта сохраняет прежний результат (существующий инвариант).
- **Чтение:** `Store.RatingRows` дополняется данными для Round Swing: раунды с `equip_*`, `plant_ms`, `side_a`, `winner`, `restored` и убийства с временем и ассистами для матчей с `result_version >= 4`. Объём — тысячи строк, расчёт на каждый запрос, как сейчас.

### 5. Использование в `internal/rating` и API

- `MatchRow` получает `Swing float64` (сумма за матч), `SwingRounds int`, `HasSwing bool`. `Build` считает Round Swing по матчу перед шагом EMA и усредняет `MatchValue`.
- `Step` хранит `Value`. `SessionChange` и `Last` возвращают взвешенное значение вместо суммы счётчиков.
- API: `score` в `PlayerView` больше не считается в `newPlayerView`. Он заполняется из книги для строк матча, итогов сессии, разбивок профиля по сессиям и матчам, а также для «Среднего за 20». У итогов периода, карт и таблицы игроков оценки нет: на экранах её там и не было.

### 6. Шкала 0–100

`k = 3` сохраняется, `r0` пересчитывается на копии БД после пересчёта: `r0 = среднее значение − ln(1.5)/k` (среднее → 60). Выбранные значения записываются сюда и в roadmap. История оценок сдвигается один раз — это ожидаемо.

### 7. Интерфейс

Новых экранов нет. Подсказки: заголовок OVR — «Общий уровень по всем матчам: Rating 2.0 и вклад в исход раундов, последние матчи весят больше»; «Оценка» — «Оценка за матч, 0–100: Rating 2.0 и вклад в исход раундов…». README — раздел о Round Swing.

## Risks / Trade-offs

- [Константы модели — допущения, а не обучение] → опорные числа HLTV и проверки на наших раундах (доля верно предсказанных победителей по шансу на момент убийств выше 50%, шансы в разумных пределах) записываются в тестах. Уточнение — вместе с 1.3.
- [Модель описывает про-сцену] → в дружеских играх перевес может решать меньше или больше; опорные точки задают только порядок величин, разницу покажет 1.3.
- [Игрок вышел посреди матча, расклад живых считается от состава матча] → известное ограничение, как у ADR; Round Swing таких раундов неточен.
- [Пересчёт всех демок при старте (4.8 ГБ)] → идёт в фоне по одной, прежние результаты видны; до пересчёта матч учитывается по Rating 2.0.
- [Заслуга без доли урона] → убийце 0.75, ассистенту 0.25 — упрощение HLTV, где заслуга делится по последнему урону, доле урона и флешке.

## Migration Plan

Миграция 006 добавляет колонки со значением 0. После деплоя сервис ставит все матчи на пересчёт (`ProcessingVersion = 4`), до его окончания значение матча — Rating 2.0. Откат кода безопасен: новые колонки старой версией не читаются.

## Open Questions

- `bPlant` и масштаб 0.03 — допущения; уточняются в 1.3 по прошлым матчам без изменения подхода.
