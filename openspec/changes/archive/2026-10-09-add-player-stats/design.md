# Design

## Context

Мотивация описана в proposal.md, требования — в specs/player-stats. Что есть сейчас:
- `match_players` хранит сырые счётчики игрока за матч, а также `team` и `result`. Производные показатели (`stats.Counters.KD/ADR/...`, rating HLTV 1.0) считаются при чтении.
- `store.SessionPlayers` (`internal/store/aggregate.go`) суммирует счётчики по `steam_id` для матчей сессии с `has_result = 1`, ник берёт подзапросом из последнего по `ordinal` матча сессии.
- `api.newPlayerView` (`internal/api/views.go`) превращает счётчики в `PlayerView` с производными, SteamID отдаётся строкой. Сортировку по rating делает обработчик сессии.
- Фронт: страницы сессий, сессии и матча на react-router; `PlayersTable` с пропом `session` для сводной таблицы; ник ведёт в Steam.

## Goals / Non-Goals

**Goals:**
- Один построитель условий выборки для таблицы, профиля и итогов сессии, чтобы правила (`has_result`, период, ник) не расходились.
- Без миграций и без поднятия `ProcessingVersion`: только чтение существующих данных.

**Non-Goals:**
- Кэширование агрегатов или материализованные таблицы. Объём — сотни матчей, запросы по `match_players` с JOIN укладываются в миллисекунды.
- Фильтр по карте в общей таблице, тренды и графики, связи между игроками.
- Пагинация таблиц и списка матчей профиля.

## Decisions

### 1. `MatchFilter` и общий построитель WHERE
В `internal/store` появляется
`MatchFilter{From, To string; SessionIDs []int64; PlayerIDs []uint64; Together bool}`
и функция, возвращающая фрагмент `WHERE` с аргументами для запросов вида
`FROM match_players mp JOIN matches m ON m.id = mp.match_id JOIN sessions s ON s.id = m.session_id`:
- всегда `m.has_result = 1`;
- `From`/`To` → `s.date >= ?` / `s.date <= ?` (даты хранятся как `YYYY-MM-DD`, строковое сравнение корректно);
- `SessionIDs` → `m.session_id IN (?, ...)`;
- `Together` при `len(PlayerIDs) > 0` →
  `m.id IN (SELECT match_id FROM match_players WHERE steam_id IN (...) GROUP BY match_id HAVING count(DISTINCT steam_id) = N)`.

Фильтр по строкам игроков (`mp.steam_id IN (...)`) добавляет только общая таблица. Профиль сам фильтрует по одному `steam_id`.

Store не проверяет взаимоисключение дат и сессий: это правило API. Store корректно работает и с обоими условиями сразу, применяя их пересечение.

*Альтернатива:* отдельный запрос под каждую страницу. Отвергнута: правило `has_result` и логика ника продублировались бы в четырёх местах.

### 2. Агрегирующие запросы
- `PlayerTotals(ctx, f MatchFilter, minMatches int) ([]PlayerTotal, error)`: `GROUP BY mp.steam_id HAVING count(*) >= ?`. `PlayerTotal` — переименованный `SessionPlayer` (`SteamID, Name, Aggregate`).
- `SessionPlayers(ctx, id)` = `PlayerTotals(ctx, MatchFilter{SessionIDs: []int64{id}}, 1)`. Публичная сигнатура и поведение сессии не меняются, существующие тесты должны пройти без правок.
- Профиль:
  - `PlayerSessions(ctx, steamID, f)` (`GROUP BY m.session_id`, вместе с датой и названием сессии);
  - `PlayerMaps(ctx, steamID, f)` (`GROUP BY m.map`);
  - `PlayerMatches(ctx, steamID, f)` (строки `match_players` с картой, счётом, `ordinal` и сессией).
- Список сумм из 14 счётчиков и соответствующий `Scan` выносятся в общие константу и функцию, чтобы не дублировать их в четырёх запросах.
- Существование игрока и ник для заголовка профиля API получает из `PlayerTotals(MatchFilter{PlayerIDs: {id}}, 1)` без периода: пустой ответ означает 404. Так 404 отличается от пустого периода без отдельного запроса.
- `SessionPlayer` переименован в `PlayerTotal`; общие для разбивок поля (`Matches`, `Wins`, `stats.Counters`) вынесены во встраиваемую структуру `Aggregate`.

### 3. Ник из последнего матча выборки
Ник берётся коррелированным подзапросом с тем же WHERE, что и основной запрос, и сортировкой
`ORDER BY s.date DESC, s.id DESC, m.ordinal DESC LIMIT 1`.
Для одной сессии это совпадает с нынешним «последний по `ordinal`». Аргументы WHERE передаются в запрос дважды.

*Альтернатива:* оконная функция `ROW_NUMBER()` по `steam_id`. Она тоже поддерживается SQLite, но подзапрос нагляднее и повторяет уже проверенный подход.

### 4. API
- `GET /api/players` → `{"players": [PlayerView...]}`, сортировка по rating по убыванию, как у сессии.
  Параметры: `from`, `to`, `session` (повторяется), `player` (повторяется, SteamID64), `together=1`, `minMatches` (по умолчанию 1).
- `GET /api/players/{steamId}` с параметрами `from`, `to`, `session`. Ответ:
  ```
  {steamId, name, totals: PlayerView,
   sessions: [{session: Session, ...PlayerView}],
   maps: [{map, ...PlayerView}],
   matches: [{matchId, sessionId, sessionDate, sessionTitle, ordinal, map, scoreA, scoreB, ...PlayerView(team, result)}]}
  ```
  Ник профиля берётся из последнего матча игрока без учёта периода, чтобы заголовок страницы не менялся от фильтра. Если в периоде пусто, `totals` нулевой, массивы пустые.
- Разбор фильтров — общая функция `parseFilter(r) (store.MatchFilter, error)`. Сообщения ошибок на русском. Ошибка «укажите либо даты, либо сессии» возвращается, если заданы и даты, и `session`.
- Список вариантов для мультивыбора игроков фронт берёт из `GET /api/players` без фильтров, сессий — из `GET /api/sessions`. Отдельные эндпоинты не нужны.

### 5. Фронтенд
- Состояние фильтров хранится в `useSearchParams` с теми же именами, что параметры API. Строка запроса почти без преобразований передаётся в API.
  Единственное отличие — `minMatches`: при отсутствии в URL UI подставляет 3 и передаёт в API явно.
- `PeriodFilter` — общий компонент страницы игроков и профиля: радиокнопка «даты / сессии», два `<input type="date">` или список сессий с чекбоксами. При переключении режима параметры другого режима удаляются из URL.
  Режим «сессии» без выбранных сессий помечается в URL параметром `period=sessions`: иначе он сбрасывался бы в «даты» до первого выбора. Сервер этот параметр игнорирует.
  Изменение фильтра создаёт запись истории (общий хелпер `updateParams` в `web/src/filters.ts`), кроме ввода порога матчей: он заменяет текущую запись, чтобы не плодить историю на каждую цифру.
- Мультивыбор игроков — список чекбоксов с никами, отсортированный по нику, без поиска (игроков десятки). Галочка «только совместные» неактивна, пока не выбрано хотя бы два игрока.
- `PlayersTable`: проп `session` переименовывается в `aggregate`, ник становится `Link` на `/players/:steamId`. Ссылка на Steam остаётся только в шапке профиля.
- Шапка: `Сессии | Игроки`.

## Risks / Trade-offs

- [Повтор аргументов WHERE для подзапроса ника] → построитель возвращает `(sql, args)`, запрос собирает аргументы явно; тест на ник за период ловит рассинхрон.
- [Динамический `IN (?, ...)` при длинных списках] → длина ограничена числом сессий и игроков (десятки), лимит параметров SQLite (32766) недостижим. Плейсхолдеры генерируются, значения не подставляются в SQL строкой.
- [ADR игроков, зашедших посреди матча, делится на все раунды] → известное ограничение парсера, наследуется агрегатами без изменений.
- [Переименование `session` → `aggregate` в `PlayersTable` затрагивает страницу сессии] → проверяется headless-браузером вместе с новыми страницами.

## Migration Plan

Миграций БД нет. Развёртывание — обычная пересборка образа. Откат — предыдущий образ, данные не меняются.
