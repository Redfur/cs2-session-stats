# Spec Delta

## Purpose

Определяет идентификаторы групп, сессий, матчей и загрузок: неугадываемые строки с префиксом типа, которые нельзя найти перебором и которые единообразно используются в адресах страниц, API и CLI.

## ADDED Requirements

### Requirement: Формат идентификатора объекта
Идентификатор группы, сессии, матча и загрузки SHALL быть строкой из префикса типа (`g_` — группа, `s_` — сессия, `m_` — матч, `imp_` — загрузка) и 12 символов алфавита `0-9A-Za-z`, выбранных криптографически стойким генератором случайных чисел. Идентификатор SHALL присваиваться при создании объекта и не меняться.

#### Scenario: Создание группы
- **WHEN** пользователь создаёт группу
- **THEN** её `id` в ответе имеет вид `g_` и 12 символов `0-9A-Za-z`, например `g_k3Xq9wTb2LpA`

#### Scenario: Идентификаторы не идут по порядку
- **WHEN** в одной группе подряд создаются две сессии
- **THEN** их id не являются соседними значениями какой-либо последовательности и по одному нельзя вычислить другой

#### Scenario: Переименование не меняет id
- **WHEN** пользователь меняет дату или название сессии
- **THEN** id сессии и адрес её страницы остаются прежними

### Requirement: Отказ на числовой и чужой идентификатор
Запрос к API или странице с идентификатором, который не соответствует формату ожидаемого типа (числовой, с префиксом другого типа, другой длины), SHALL обрабатываться как запрос к несуществующему объекту: тот же код ответа и текст «не найдено», что и для отсутствующего id верного формата.

#### Scenario: Старый числовой адрес
- **WHEN** открыт `GET /api/sessions/3`
- **THEN** ответ — 404 с текстом «сессия не найдена», как для несуществующей сессии

#### Scenario: Префикс другого типа
- **WHEN** в `GET /api/matches/{id}` передан id сессии `s_…`
- **THEN** ответ — 404 с текстом «матч не найден»

#### Scenario: Числовой адрес страницы
- **WHEN** пользователь открывает `/g/1/sessions/3`
- **THEN** страница показывает состояние «не найдено» и не перенаправляет на другой объект

### Requirement: Нет числовых идентификаторов объектов в API
Ответы и тела запросов API SHALL ссылаться на группы, сессии, матчи и загрузки только строковыми идентификаторами — в полях `id`, `groupId`, `sessionId`, `matchId`, `importId`, `matchIds` и любых других ссылках на эти объекты. Внутренние порядковые номера хранения SHALL NOT попадать в ответы и SHALL NOT приниматься API. SteamID игроков и номера раундов, карт и матчей платформ это требование не затрагивает.

#### Scenario: Ответ сессии
- **WHEN** запрошена сессия с матчами
- **THEN** `id`, `groupId` сессии, `id` и `sessionId` каждого матча — строки с префиксами `s_`, `g_`, `s_`, `m_`

#### Scenario: Порядок матчей
- **WHEN** клиент меняет порядок матчей сессии
- **THEN** он передаёт список строковых id матчей, а список с числами отклоняется

#### Scenario: Результат добавления ссылки
- **WHEN** ссылка на матч уже загружена в другую сессию
- **THEN** ответ ссылается на существующие матч и сессию их строковыми id

### Requirement: Последняя группа в браузере
Если сохранённая в браузере последняя открытая группа отсутствует в списке групп (в том числе сохранённая в старом числовом формате), интерфейс SHALL открыть первую доступную группу и перезаписать сохранённое значение.

#### Scenario: Сохранён числовой id
- **WHEN** в браузере сохранена группа `1`, а пользователь открывает `/`
- **THEN** открывается первая группа из списка, и в браузере сохраняется её строковый id

### Requirement: Переход существующих данных
При обновлении сервиса существующие группы, сессии, матчи и загрузки SHALL получить идентификаторы нового формата с сохранением всех связей и результатов. Порядок списков групп, сессий одной даты, матчей, очередей разбора и скачивания и хронология рейтинга SHALL остаться прежними; статистика, дуэли и OVR SHALL совпасть со значениями до обновления без повторного разбора демок.

#### Scenario: Статистика после обновления
- **WHEN** сервис запускается на базе с прежними числовыми id
- **THEN** таблица игроков, профили и OVR каждой группы совпадают со значениями до обновления, а матчи не ставятся на повторный разбор

#### Scenario: Порядок сессий одной даты
- **WHEN** в группе были две сессии одной даты
- **THEN** после обновления они идут в списке и в хронологии рейтинга в прежнем порядке

#### Scenario: Очередь сохраняется
- **WHEN** на момент обновления в очереди скачивания стояли две ссылки
- **THEN** после обновления они скачиваются в прежнем порядке

### Requirement: Строковые id в CLI
Команда `cs2stats reparse` SHALL принимать в `--session` и `--match` строковые идентификаторы соответствующего типа и отклонять значение другого формата с сообщением об ошибке.

#### Scenario: Пересчёт сессии
- **WHEN** выполнено `cs2stats reparse --session s_Vf8nR2pQxa7c`
- **THEN** матчи этой сессии ставятся на пересчёт и выводится их число

#### Scenario: Числовой id в CLI
- **WHEN** выполнено `cs2stats reparse --match 5`
- **THEN** команда завершается ошибкой о неверном id матча и ничего не ставит в очередь
