# Design

## Context

См. proposal.md — Why. Текущее состояние:

- `groups`, `sessions`, `matches`, `imports` — `id INTEGER PRIMARY KEY`; на них ссылаются `sessions.group_id`, `matches.session_id`, `matches.import_id`, `imports.session_id` и `match_id` семи таблиц результата (`match_players`, `match_duels`, `match_player_ext`, `match_player_weapons`, `match_rounds`, `match_kills`, `match_clutches`), все с `ON DELETE CASCADE` (кроме `matches.session_id` и `sessions.group_id`).
- Структуры `store.Group/Session/Match/Import` сериализуются в JSON напрямую; id — `int64`. API разбирает путь через `pathID` (`strconv.ParseInt`).
- Возрастающий id задаёт порядок: `ClaimNextPending` — `ORDER BY has_result, id`, очередь скачиваний и выборки загрузок — `ORDER BY id`, `ListGroups` — `ORDER BY g.id`, тай-брейк сессий одной даты — `s.date, s.id` в рейтинге, агрегатах, дуэлях, расширенной статистике.
- `created_at` — RFC 3339 с точностью до секунды; ссылки одной партии вставляются в одну секунду, поэтому для порядка он не годится.
- DSN включает `foreign_keys(1)`; раннер `migrate` выполняет каждый SQL-файл в своей транзакции и пишет `PRAGMA user_version`.
- `internal/rating` сравнивает id матча и сессии только на равенство.
- Фронт: `paths` и `useGroupId` уже работают со строками, `pickGroup` при отсутствии сохранённой группы берёт первую; числовые типы — в `web/src/api.ts` (`id`, `groupId`, `sessionId`, `matchId`, `importId`, `reorderMatches(matchIds: number[])`, `retryImport/deleteImport(id: number)`) и нескольких компонентах (`SessionPage.ordinalOf`, `ExtStats.ExtNotComputed`). `upload.ts` нумерует файлы очереди локальным счётчиком — это не id сервера, он не меняется.

## Goals / Non-Goals

**Goals:**
- Ни один путь, ответ или тело запроса API не содержит целых id групп, сессий, матчей, загрузок; это проверяется тестом.
- Переход без пересчёта демок и без изменения статистики, OVR и порядка.

**Non-Goals:**
- Защита доступа: неугадываемый id не заменяет авторизацию, права появятся с `add-steam-auth`.
- Публичное API, API key, версионирование API.
- Короткие «красивые» адреса и коды для приглашений (у приглашений будут свои токены).

## Decisions

### Формат: префикс + 12 символов base62

`internal/ids`: `New(kind) string` — 12 символов из `crypto/rand`, выбор символа отбором без смещения (байт ≥ 248 отбрасывается, остальные `% 62`); `Valid(kind, s) bool` — точная длина, префикс и алфавит. Типы — константы `Group = "g_"`, `Session = "s_"`, `Match = "m_"`, `Import = "imp_"`.

62¹² ≈ 3,2·10²¹ (~71 бит): перебор невозможен, вероятность коллизии на миллионе объектов ~10⁻¹⁰. Коллизию всё равно ловит `PRIMARY KEY`: вставка повторяется с новым id (до 3 попыток), затем ошибка.

Альтернативы: UUIDv4 (36 символов в адресе без выгоды — в SQLite это тот же текст), UUIDv7/ULID (раскрывают время создания, выгода по локальности индекса на наших объёмах не нужна), Sqids поверх чисел (обратимы, перебор остаётся). Префикс — удобство (тип виден в логах и ошибках будущего публичного API), на стойкость не влияет; решение пользователя.

### Строковый первичный ключ, а не колонка `public_id`

Решение пользователя: целых id объектов в схеме не остаётся, поэтому утечь им неоткуда; смена типа `int64 → string` по всем пакетам ловится компилятором. Цена — пересборка таблиц в миграции.

### Внутренняя колонка `seq` для порядка

У `groups`, `sessions`, `matches`, `imports` появляется `seq INTEGER NOT NULL UNIQUE`: для существующих строк — старый id, для новых — `(SELECT coalesce(max(seq), 0) + 1 FROM <table>)` в том же `INSERT` (запись идёт под `_txlock=immediate`, гонки нет). Все `ORDER BY … id` и тай-брейки `s.id`/`m.id` заменяются на `seq`. `seq` не входит в JSON-структуры (поле в Go не объявляется вовсе) и не принимается API.

Альтернативы: `rowid` таблицы без `INTEGER PRIMARY KEY` (SQLite вправе перенумеровать его при `VACUUM`), `created_at` с наносекундами (не монотонен между процессами, хрупко). `seq` — не идентификатор: по нему ничего не ищется, кроме сортировки.

### Миграция `008_string_ids`: Go-шаг + SQL

Сгенерировать base62 из `crypto/rand` в SQL нельзя, поэтому раннер `migrate` получает реестр Go-шагов по номеру миграции (`Before`/`After` — `func(ctx, *sql.Tx) error`), которые выполняются в той же транзакции до и после SQL-файла. Шаг 008 создаёт временные таблицы соответствия `id_map_groups/sessions/matches/imports (old INTEGER PRIMARY KEY, new TEXT NOT NULL UNIQUE)` и заполняет их `ids.New`.

SQL 008 в той же транзакции (`foreign_keys` внутри транзакции не выключить, поэтому пересборка устроена так, чтобы ссылки не нарушались ни на одном шаге):
1. `ALTER TABLE <t> RENAME TO <t>_old` для всех 11 таблиц: SQLite сам переписывает ссылки дочерних таблиц на `*_old`, старая структура остаётся связной.
2. `CREATE TABLE <t>` под итоговыми именами с `TEXT` ключами, `seq` у четырёх основных, теми же ограничениями, `sessions.group_id NOT NULL`; `REFERENCES` указывают на новые таблицы.
3. `INSERT INTO <t> SELECT …` от родителей к детям с заменой ключей через `LEFT JOIN id_map_*` (ссылка без соответствия даёт `NULL` и падает на `NOT NULL`, а не теряет строку); `seq` = старый id.
4. `DROP TABLE <t>_old` от детей к родителям: каскады неявного `DELETE` задевают только старые таблицы. Затем `DROP` таблиц соответствия и индексы заново (старые индексы ушли вместе с `*_old`).
5. Go-проверка `PRAGMA foreign_key_check` после SQL (пусто, иначе откат). Тест миграции проверяет, что число строк каждой таблицы не изменилось и в схеме не осталось ссылок на `*_old`.

Первоначальный вариант (`<t>_new` с `REFERENCES` на итоговые имена и `defer_foreign_keys`) не работает при включённых внешних ключах: строки новых дочерних таблиц, вставленные, пока под итоговым именем лежит старый родитель, накапливают отложенные нарушения, и `COMMIT` падает.

Порядок `has_result`/`status`/`processed_version`/`result_version` переносится как есть, поэтому `ProcessingVersion` и пересчёт не задеваются.

Альтернатива — переписать всё на Go (чтение и вставка построчно): медленнее на таблицах `match_kills` и дублирует схему в коде.

### Разбор id в API

`pathID(w, r)` → `pathKey(w, r, name, kind, notFound string) (string, bool)`: невалидный по `ids.Valid` id отвечает 404 с тем же текстом, что `store.ErrNotFound`, без обращения к базе. Тела запросов (`reorderRequest.MatchIDs []string`) проверяются так же; неверный id в списке — 400, как сейчас при несовпадении состава матчей.

### Тест-страж

Тест в `internal/api` поднимает тестовый сервер с группой, сессией, матчем с результатом и загрузкой, обходит основные GET-эндпоинты (группы, сессии, сессия, матч, ext, дуэли, игроки, профиль и вкладки, загрузки) и рекурсивно проверяет JSON: значение ключа `id`, `*Id` или `*Ids` (кроме `steamId`, `killerId`, `victimId`, `assisterId`, `externalId`) не может быть числом. Новый эндпоинт без строки в этом списке — повод дописать тест.

### Фронт: порядок без id

Сортировка матчей профиля «по времени» строила ключ из даты, id сессии и номера матча. Со случайными id тай-брейк сессий одной даты потерял бы смысл, поэтому ключ — позиция матча в ответе сервера (сервер уже отдаёт матчи по дате, `seq` сессии и номеру). Сохранённая последняя группа, которой нет в списке, заменяется первой в `pickGroup`.

### CLI

`reparse` читает `--session`/`--match` как строки и проверяет `ids.Valid`; сообщение об ошибке — «неверный id сессии/матча».

## Risks / Trade-offs

- [Миграция трогает всю базу] → бэкап перед обновлением (`README`), тест миграции на синтетической базе со всеми таблицами, E2E на копии `data/` со сверкой таблицы игроков и OVR до/после.
- [Внешние закладки с числовыми адресами ломаются] → принято пользователем; сервис ещё не публичный.
- [Строковые ключи медленнее целых в соединениях] → на объёмах компании друзей незаметно; индексы по `match_id` остаются.
- [`seq` выглядит как скрытый целый id] → он не принимается API и не сериализуется; тест-страж ловит появление числовых `id`-полей.
- [Забытое место, где id собирается из числа на фронте] → `tsc` после смены типов в `api.ts`, проход по страницам в headless-Chromium.

## Migration Plan

1. Остановить сервис, сделать копию `data/cs2stats.db*`.
2. Запустить новую версию: миграция 008 выполняется при старте в одной транзакции; при ошибке база остаётся в версии 7.
3. Откат: остановить сервис и вернуть копию базы, запустить прежнюю версию (обратной миграции нет).
