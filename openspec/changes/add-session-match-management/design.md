# Design

## Context

Зачем это нужно, см. proposal.md. Текущее состояние, которое определяет подход:

- `matches.session_id` ссылается на `sessions` **без** `ON DELETE CASCADE`, при этом `foreign_keys(1)` включён. Поэтому сессию с матчами удалить нельзя, пока матчи не удалены явно. `match_players` удаляется каскадом вместе с матчем.
- `UNIQUE (session_id, ordinal)` и `ordinal = max + 1` при `AddMatch`. Наивный сдвиг номеров одним `UPDATE` может нарушить уникальность на промежуточной строке.
- `matches.sha256 UNIQUE` используется для дедупа. Файл демки лежит в `ingest.Storage` (`data/demos/<sha256>.dem`), его путь однозначно задаётся sha.
- Загрузка в `ingest.Service.Ingest` идёт так: распаковка, затем `FindMatchBySHA`, затем `Demos.Save` (rename), затем `Store.AddMatch`.
- Воркер держит открытым файл демки, пока парсит, а результат сохраняет транзакцией `SaveMatchResult`. Если строки матча нет, транзакция откатывается: `UPDATE` затрагивает 0 строк (`ErrNotFound`), либо раньше срабатывает FK при вставке игроков. Последующий `FailMatch` обновляет 0 строк.

## Goals / Non-Goals

**Goals:**
- Удаление атомарно на уровне БД: после ответа API не остаётся «полуудалённых» сессий и матчей с дырами в нумерации.
- Удаление файла демки не мешает параллельной загрузке той же демки.
- Без миграции схемы.

**Non-Goals:**
- Мягкое удаление и восстановление.
- Перестановка drag-and-drop: в прототипе достаточно кнопок ↑/↓.
- Отмена уже идущего парсинга удаляемого матча: воркер просто доработает и не сохранит результат.

## Decisions

### 1. Сначала БД, потом файлы
Строки удаляются в одной транзакции, файлы демок удаляются после коммита по принципу best-effort. Ошибка удаления файла пишется в лог, а API всё равно отвечает успехом.
- *Альтернатива:* сначала файлы, потом БД. Если транзакция упадёт, у живого матча не останется демки, и его нельзя будет пересчитать. Файл-сирота без матча безвреден: повторная загрузка той же демки перезапишет его через rename.

### 2. Мьютекс в `ingest.Service` против гонки с загрузкой
Окно гонки выглядит так: удаление закоммитило БД → загрузка той же демки сделала `Save` (перезаписала файл) → удаление стёрло файл → загрузка сделала `AddMatch`. В итоге матч без демки.
Решение: в `ingest.Service` появляется `sync.Mutex`. Им защищён участок `FindMatchBySHA → Save → AddMatch` при загрузке и новый метод `RemoveDemos(ctx, shas)`, который под тем же мьютексом для каждого sha проверяет `FindMatchBySHA` и удаляет файл только если матча с этим sha нет. Распаковка (долгая часть) идёт вне мьютекса, под ним только rename и insert.
- *Альтернатива:* принять риск. Сервис однопользовательский, но цена ошибки — тихо сломанный матч, а защита занимает несколько строк. Сервис — один процесс, поэтому мьютекса в памяти достаточно (CLI `reparse` файлы не загружает и не удаляет).

### 3. Каскад сессии делается кодом, а не миграцией
`DeleteSession` в транзакции выбирает sha матчей сессии, удаляет её `matches` (`match_players` уходят по существующему каскаду), затем саму сессию, и возвращает список sha для `RemoveDemos`.
- *Альтернатива:* миграция с `ON DELETE CASCADE` на `matches.session_id`. В SQLite для этого пришлось бы пересоздавать таблицу `matches`, а sha всё равно нужно собрать заранее. Выигрыша нет.

### 4. Перенумерация в две фазы
Общий хелпер `renumber(tx, sessionID, ids)`: сначала `ordinal = -ordinal` для всех матчей сессии, затем `ordinal = i+1` по порядку `ids`. Отрицательные значения не пересекаются с положительными, поэтому `UNIQUE` не нарушается. Хелпер используют `DeleteMatch` (порядок `ids` = текущий порядок без удалённого) и `ReorderMatches`.

### 5. Порядок передаётся полным списком
`PUT /api/sessions/{id}/order` с телом `{"matchIds": [3, 1, 2]}`. Сервер проверяет, что набор id совпадает с матчами сессии: без повторов, без пропусков, без чужих. Иначе 400 с текстом «список матчей не совпадает с матчами сессии», и UI перезагружает сессию. Ответ — список матчей сессии в новом порядке.
- *Альтернатива:* `PATCH /api/matches/{id}` с `{"ordinal": n}` или эндпоинт «сдвинуть вверх». Такой запрос не видит устаревшего состояния (например, пока пользователь смотрел страницу, догрузили матч). Полный список явно ловит рассинхрон и годится для будущего drag-and-drop.

### 6. Контракт API
| Метод | Тело | Успех | Ошибки |
|---|---|---|---|
| `PATCH /api/sessions/{id}` | `{"date": "...", "title": "..."}`, оба поля обязательны | 200 + сессия | 400 валидация, 404 |
| `DELETE /api/sessions/{id}` | — | 204 | 404 |
| `DELETE /api/matches/{id}` | — | 204 | 404 |
| `PUT /api/sessions/{id}/order` | `{"matchIds": [...]}` | 200 + `[]Match` | 400, 404 |

Валидацию даты и названия выносим из `createSession` в общий хелпер. В отличие от создания, пустая дата при редактировании — ошибка: подставлять «сегодня» при правке неожиданно. Обработчики удаления: store-метод → `s.Ingest.RemoveDemos` → ошибки удаления файлов в `s.Log.Warn`.

### 7. Фронтенд
- Клиент `request` в `api.ts` уже переживает пустое тело (`resp.json().catch(() => null)`), поэтому для 204 правки не нужны. Методы удаления типизируются как `Promise<void>`.
- `SessionPage`: шапка с кнопкой «Изменить», которая превращает её в форму даты и названия (как на `SessionsPage`), и «Удалить сессию» с `confirm` («Удалить сессию и N матчей вместе с демками?»), затем `navigate('/')`.
  В таблице матчей колонка действий: ↑ (неактивна у первого), ↓ (неактивна у последнего), «Удалить» с `confirm`. Пока идёт запрос, все кнопки действий неактивны; после ответа вызывается `load()`.
  Ошибка действия хранится в отдельном состоянии: `load()` при успехе сбрасывает ошибку загрузки и иначе стёр бы ошибку перестановки сразу после её показа.
- `MatchPage`: «Удалить матч» с `confirm`, затем `navigate('/sessions/:sessionId')`.

## Risks / Trade-offs

- [Удаление необратимо, а авторизации нет] → подтверждение в UI; в README напомнить, что сервис не выставляется наружу без reverse proxy, и что `data/` стоит бэкапить.
- [Удаление матча во время парсинга оставляет в логе предупреждение «матч не обработан» с ошибкой FK или «не найдено»] → это безвредно, поведение фиксируется тестом воркера. Отдельная обработка не нужна.
- [Файл-сирота при ошибке удаления] → запись в лог; повторная загрузка перезапишет файл. Чистка сирот при старте не входит в этот change.
- [Переиспользование id: таблицы без `AUTOINCREMENT`, поэтому после удаления сессии или матча с наибольшим id новая запись получает тот же id, и старая ссылка откроет другую сессию или матч] → для прототипа приемлемо: ссылки на удалённое никто не хранит. Если станет мешать, это отдельный change с миграцией (пересоздание таблиц с `AUTOINCREMENT`).
- [Устаревший список при перестановке (две вкладки)] → 400 и перезагрузка данных в UI (решение 5).

## Migration Plan

Миграции БД нет. Выкатка — обычная пересборка образа. Откат — предыдущий образ: новые эндпоинты исчезнут, данные совместимы. Удалённые данные откатом не восстанавливаются.
