# Design

## Context

Сейчас `parser.Match` содержит игроков и раунды, `Kill` — время, участников и headshot, `Damage` — участников и урон. Нет оружия/времени урона, бросков, ослеплений и снимков живых участников. `stats.Compute` считает базовые K/D/A, урон, KAST, открытия и мультикиллы; KAST использует окно размена 5 секунд. Отдельных счётчиков разменов и клатчей нет. `K5` означает 5 и более убийств.

Основные события уже доступны в [demoinfocs v5.2.0](https://github.com/markus-wa/demoinfocs-golang/blob/v5.2.0/pkg/demoinfocs/events/events.go): Kill, PlayerHurt, WeaponFire, GrenadeProjectileThrow, PlayerFlashed, RoundEnd. Это подтверждает кандидатов для реализации, но не полноту и качество данных конкретных демок. В частности, PlayerFlashed.FlashDuration читает состояние игрока; перекрывающиеся флешки требуют отдельной проверки.

Исходные демки сохраняются; успешный результат пересчёта заменяет старый атомарно. Это позволяет добавить новые результаты без загрузки файлов заново. Не следует считать старую успешно обработанную демку автоматически покрытой новыми метриками.

## Goals / Non-Goals

Цель: обеспечить данные для дополнительной статистики профиля, сохранив возможность объяснить каждое значение через события, формулу, версию и покрытие.

Не входит: дизайн экрана, реализация личных дуэлей, изменение KAST/рейтинга/мультикиллов, расчёт OVR, воспроизведение закрытых методик Scope, автоматическая смена источника исторических профилей. Новый источник обозначается `demo`; совпадение названий не означает совпадение определений.

## Decisions

Все технические решения этого раздела — предлагаемый вариант для ревью разработчиком. После ревью спорные определения необходимо закрепить в spec до реализации.

### 1. Границы данных и идентификация

- Сохранять SteamID64, идентификаторы матча/раунда, игровой tick и порядок события; использовать время демо, не настенные часы.
- Для новых active-метрик отношения «союзник/противник» определять по составу на момент события; personal-duels продолжает использовать baseline-команду матча. Перемена сторон не меняет личность игрока; смена состава между картами не переносит командную принадлежность.
- Текущие базовые вычисления оставить совместимыми. Для новых показателей зафиксировать фазу: активная часть принятого раунда от окончания freeze time до первого RoundEnd включительно. Исключить warmup, knife и отменённые раунды. Это отдельное определение, не обещание равенства базовым суммам, включающим постраундовые события.
- Снимок участников и живых игроков обязателен для клатчей. Дисконнект не считать убийством; потеря достоверности состава делает затронутые раунды непригодными для клатчей. Для незавершённого раунда без достоверного результата не вычислять победу/поражение в клатче.

### 2. Размены

Предложение: смерть A от противника B разменяна, если живой союзник C убивает B в том же раунде спустя `0 < Δt <= 5 секунд`. События одного tick не объявлять причинным разменом по случайному порядку callback. Точные tick/time правила согласовать и версионировать.

Хранить связи исходной смерти и ответного убийства. Отдельные счётчики: число разменянных смертей игрока и число его убийств, совершённых в размен. Если B убил двух союзников C, одно убийство B может разменять обе смерти: у C одно trade kill, у жертв по одной traded death. Самоубийства, teamkill, world kill и события за границами раунда исключаются. Существующий KAST этим изменением не пересчитывается по новой методике.

### 3. Клатчи

Предложение: попытка начинается при первом достоверном состоянии «один живой игрок против N живых противников» в активном раунде. Не более одной попытки на игрока за раунд. N фиксируется при начале; 1v3 → 1v2 → 1v1 остаётся одной попыткой 1v3. В одном раунде попытки могут возникнуть у игроков обеих команд.

Победа определяется итогом раунда для команды игрока, включая бомбу; выживание не обязательно. Итог неизвестен — попытка остаётся unresolved и исключается из win rate. Использовать состояние после обработки всех событий одного tick, чтобы исключить ложные промежуточные 1vN. Нужны проверки изменений состава, одновременных смертей и реконструированного последнего раунда. Хранить attempts, wins, losses, draws, unresolved для каждого N; attempts = wins + losses + draws + unresolved. Наблюдаемая ничья — draws, не поражение и не неизвестный исход; win rate = wins / (wins + losses), при нулевом знаменателе null. Не начинать попытку по состоянию, появившемуся только после RoundEnd; N должен быть >= 1. Утрата достоверности после начала попытки оставляет её unresolved, если исход для неё нельзя подтвердить.

### 4. Оружие и наблюдаемые данные стрельбы

Оружие брать из события выстрела/урона/убийства, а не из текущего предмета в руках. Хранить исходный тип и версию нормализации. Неатрибутированное оружие выделять как unknown; не записывать урон огня как урон оружия, которое игрок держал в тот момент.

По оружию: enemy kills, headshot kills, фактический enemy health damage, число событий выстрела и попаданий с известным hitgroup. Проверить значение «выстрел» для дробовиков, очередей и пробитий на демках. События урона/выстрела сами по себе не дают долю успешных выстрелов: одна пуля может дать несколько попаданий. Сохранять эти счётчики, но не называть их частное процентом точности и не ограничивать его искусственно 100%.

HS по убийствам и HS по попаданиям — разные именованные показатели с собственными знаменателями. Сопоставимость hitgroup и успешных выстрелов должна быть доказана перед публикацией Accuracy. FBA, TTK/TTD и visibility/spotted-фильтрация отложены до отдельного исследования: произвольное время между выстрелом и убийством не является заменой.

### 5. Utility

Предлагаемые числители для пяти продуктовых значений:

| Показатель | Предлагаемый исходный счётчик | Правило, требующее проверки/ревью |
| --- | --- | --- |
| Урон HE | Фактический урон здоровью противников от HE | Без overkill и урона союзникам; не складывать повторно с базовым damage |
| Ослеплённые игроки | Пары «одна флешка — один противник», длительность > 0 | Повторное ослепление новой флешкой считается снова; это не уникальные люди за карту |
| Секунды ослепления | Атрибутированные интервалы ослепления противников | Правило перекрытий и авторства пока не подтверждено; до проверки значение unavailable |
| Использованные смоки | Уникальные броски smoke игроком | Считать бросок, даже если smoke не раскрылся; не считать WeaponFire и projectile throw дважды |
| Урон Molotov | Фактический урон здоровью противников от Molotov и Incendiary | Предлагается объединять в UI, сохранять исходный тип; подтвердить авторство fire damage |

Для каждой метрики `сумма числителя / число полностью покрытых карт игрока`. Карта — конкретный матч/демка, не название de_*. Карты с достоверным нулём входят в знаменатель, с отсутствующим или неполным сбором этой метрики — не входят. В ответе также общее число выбранных карт, полное/частичное покрытие и исключённые карты. При частичных данных значение относится только к покрытому подмножеству и явно так маркируется.

Секунды не суммировать слепо из PlayerFlashed.FlashDuration: новое событие может описывать уже изменённое состояние. Сначала проверить перекрытия одной/нескольких флешек, разных авторов, восстановление зрения и смерть жертвы. Точный алгоритм атрибуции остаётся блокирующим вопросом для этой метрики. Остальные проверенные счётчики могут поставляться независимо.

### 6. Хранение, API и пересчёт

- Предлагается отдельная версионированная группа результатов на матч/игрока; именованные счётчики, знаменатели и статус полноты по метрике. Конкретные SQL-таблицы и JSON-форму согласует разработчик.
- Сохранять минимальные исходные события по контракту раздела 9, связи разменов, попытки клатчей и атрибуцию гранат. Не требуется хранить каждый tick мира бессрочно. Конкретные SQL-таблицы и политику дополнительных диагностических записей определить на ревью; обязательные поля не заменяются только итоговыми суммами.
- API матча/профиля возвращает source, definitionVersion, coverage и null для неопределённого значения. Отношения агрегируются из сумм числителя/знаменателя; среднее процентов по картам не используется. Несовместимые definitionVersion/boundaryPolicy дают unavailable с причиной incompatible_definitions для общего показателя и отдельные совместимые группы; неудобная версия не исключается молча. SteamID64 в JSON — десятичная строка, как в personal-duels.
- Миграция помечает старые результаты как not calculated. Поднять версию обработки, пересчитывать исходные демки; атомарно заменять новую группу целиком. При ошибке сохранить предыдущий успешный результат с его версией и статусом устаревания. Повторный пересчёт не добавляет дубликаты.
- Новые расширенные группы имеют свои definitionVersion/processingVersion/stale-статусы; у personal-duels сохраняется result_version успешного baseline. Самостоятельный пересчёт группы сохраняет остальные результаты с их версиями и доказательными событиями; полный пересчёт публикует завершённый набор атомарно. Нельзя стереть журнал старой группы, пока на него ссылается её сохранённый результат. Удалённый матч не воскресает после завершения воркера, даже при конкурентном пересчёте.

### 7. Полученный урон и типы ассистов

Полученный урон уже можно связать с жертвой в Damage, но отдельного счётчика нет. Предлагается сохранять фактический health damage от противников и нанесённый им урон в одной активной фазе. Self/team/world damage не включать в enemy damage taken; неизвестного атакующего не считать автоматически world — сохранить причину неизвестности. Новый `demo ADRdiff = (enemy damage dealt - enemy damage taken) / covered player-rounds`. Знаменатель — полностью покрытые активные раунды игрока, включая нули. Это собственное определение, не воспроизведение Scope ADRdiff. Не менять существующий базовый Damage/ADR; новые фазовые числители хранить отдельно.

Из Kill.AssistedFlash сохранять классификацию game-reported ассиста: flash либо non-flash, только для допустимого ассистента при убийстве противника. Каждый такой ассист относится к одной категории; неизвестность типа хранится отдельно, не становится non-flash. Non-flash не объявляется доказанным damage assist. Отдельный useful flash assist этим флагом не определяется. Текущий базовый Assists остаётся по прежнему контракту; равенство новых фазовых сумм базовому счётчику не требуется.

### 8. Минимальная запись игрок/раунд

Для принятых раундов сохранять идентификатор, T/CT участника, tick/время конца freeze и RoundEnd, Reason/Winner, живой статус на конец активной фазы и время смерти в этой фазе. Начальное здоровье/состояние и присутствие проверять перед утверждением полноты; основной формат внутренних игр — полное участие всех десяти игроков. Дисконнект/повреждённые записи — технические исключения покрытия, не новая гипотеза об обычном составе.

Время жизни определять от начала активной фазы до смерти либо RoundEnd для выжившего. Постраундовую смерть сохранять с фазой, но не превращать в смерть активного раунда. Восстановленный из счёта исход помечать reconstructed: он не доказывает точные границы, причину и время выживания. При недостоверной границе/стороне соответствующие поля unavailable, а не 0 или T по умолчанию.

Участники постановки/разминирования бомбы и детали убийств входят в сбор по разделу 10. Этот change не требует универсальный журнал всех возможных событий, координаты каждого tick или новые пространственные/экономические показатели.

### 9. Минимальный сохраняемый журнал

Сохранить журнал в составе атомарного результата обработки, доступный для проверки конкретного расчёта. Формат хранения выбирает разработчик; обязательный состав:

| Запись | Обязательные значения при наличии в источнике |
| --- | --- |
| Метаданные результата | Идентификатор матча, hash исходной распакованной демки, версия парсера/обработки/определений, тип записи server/GOTV, POV либо unknown, фактически наблюдаемый диапазон, признаки обрыва/позднего начала, единицы времени и статусы покрытия |
| Общее для события | Идентификатор события в результате, исходный порядок, tick и время демо с доступной точностью, тип, раунд либо unknown, фаза (freeze/active/post-round/warmup/knife/discarded/unknown), SteamID участников и их команды/стороны при доступности, причины неизвестности |
| Kill | Killer/victim/assister, исходный и нормализованный тип оружия, headshot, AssistedFlash, ThroughSmoke, PenetratedObjects, NoScope, AttackerBlind, Distance |
| PlayerHurt | Attacker/victim, оружие, HealthDamageTaken/ArmorDamageTaken, исходные HealthDamage/ArmorDamage для диагностики, остаточные Health/Armor, hitgroup; отделить health damage от armor damage |
| WeaponFire | Shooter, оружие, исходный порядок и время; не объявлять shot-to-hit связь достоверной только из совпадения времени |
| Гранаты | Уникальный в рамках результата projectile/lifetime идентификатор либо статус unknown, тип, бросивший, событие throw/detonation/expiry при наличии; для flash — жертва, reported duration с семантикой снимка состояния и связь с projectile при доказанной атрибуции |
| Раунд/player-round | Границы, Reason/Winner, состав/живое состояние для клатча, T/CT, смерть/выживание, полнота и reconstructed статус |
| Бомба | Тип события plant begin/aborted/planted, defuse start/aborted/defused, explode; участник, site A/B/unknown, время, связь с попыткой при достоверности; HasKit для defuse start при доступности |

Raw reported duration флешки не является уже проверенными секундами ослепления. Distance сохранять с указанием исходных единиц либо unknown units; не называть значение метрами без проверенного преобразования. Нулевой damage или false flag допустимы только при подтверждённой наблюдаемости поля. Неизвестный участник не становится игроком SteamID=0: отдельно различать мир, бота и неизвестного человека/атрибуцию.

Идентификатор события должен быть однозначным внутри версии результата. Связи разменов, клатчей, гранат и попыток бомбы ссылаются на этот же результат. При повторном пересчёте не остаются ссылки на удалённые записи прежней версии. Не удалять разные события с одинаковым tick/участниками как дубликаты; исключать лишь доказанное повторное поступление одного исходного события. Сам tick не достаточен как ID. Демка остаётся источником для полного воспроизведения; дополнительные пространственные снимки не обязательны.

### 10. Детали убийств и бомба

Собирать исходные kill flags без введения новой оценки навыка. Прострел определяется из положительного PenetratedObjects; сохранять также исходный счётчик. Одно убийство может одновременно быть headshot, through smoke и wallbang — флаги не взаимоисключающие. NoScope и AttackerBlind относятся к отмеченному событию, не ко всем последующим действиям игрока. Неподтверждённый флаг хранить unknown; проверенный false сохраняется как false.

У бомбы различать начало действия, прерывание и успешное завершение. Сохранять каждую отдельную попытку, если границы видны. Если начало отсутствует, наблюдаемое завершение всё равно сохранить, но не создавать выдуманную попытку/длительность. Плент и участник не восстанавливаются из текущего держателя C4 либо победителя раунда. У abort/start defuse событие может не содержать site: перенос site допустим только из достоверно связанного состояния бомбы того же раунда; иначе unknown. При нескольких попытках не связывать завершение с первой автоматически. BombExplode не приписывается игроку только потому, что он ставил бомбу.

События, связанные с терминальным исходом раунда, могут поступать в том же tick в другом callback-порядке. Сохранять порядок и оба события; перед подсчётом проверить связь с исходом раунда, не отбрасывать успешный defuse только из-за callback после RoundEnd. Это правило терминальных событий не включает обычные постраундовые убийства в активную фазу.

### 11. Совместимость границ и качество записи

Контракт personal-duels (спека `personal-duels`, `internal/stats/duels.go`) использует те же enemy kills, что и K, с командой, закреплённой на матч; смена команды внутри карты остаётся известным ограничением. Этот change использует состав на момент события только для новых active-метрик и не меняет статус или фильтры дуэлей. Сохраняется инвариант baseline K = сумма baseline-дуэлей; их сравнение с active kills не обязано совпадать. Контроль: A убивает B до RoundEnd и C после него; базовый/дуэльный счёт содержит оба принятых убийства, новые active-счётчики — только первое. Журнал сохраняет оба события с фазами без дубликатов. API расширения выдаёт именованные boundary policy/version, прежние ответы дуэлей не переписываются.

`complete` в API дуэлей означает полноту расчёта по `has_result = 1 AND result_version >= store.DuelsSinceVersion` (сейчас 2), а не доказанную полноту исходной записи. Новое observationCoverage отражает наблюдаемость конкретной метрики и диапазон записи. Дуэли фрагмента могут оставаться complete по прежнему API, в то время как новые Utility/ADRdiff имеют partial/unavailable. Не использовать coveredMatches дуэлей как знаменатель полностью наблюдаемых карт Utility; не менять baseline-максимумы скрытым исключением фрагментов. Изменение качества самих дуэлей потребует отдельного modified requirement.

Повреждение записи снижает покрытие новых затронутых полей и метрик, а не автоматически уничтожает все результаты. Успешное чтение файла/header не доказывает полную запись. Ноль событий урона сам по себе не доказывает ни повреждение, ни корректный нулевой урон: нужна проверка поддержки/наблюдаемости, иначе damage unavailable. При POV не заявлять полноту всех игроков без проверки.

Для начала посреди матча сохранить наблюдаемый фрагмент и причины неполноты; не заполнить пропущенные раунды нулями и не получить полное per-map Utility из фрагмента. Для оборванного финала сохранить завершённые достоверные раунды, финальный незавершённый отметить отдельно; итог из scoreboard может быть reconstructed, но не доказывает полноту событий. MR12/MR3 и смены сторон в overtime проверять по фактическим раундам/счёту, не обрезать после 24 раундов и не использовать номера раундов как единственное доказательство T/CT. Исходные противоречия не исправлять молча.

### 12. Совместимость миграции и версии результата

Personal-duels реализованы: миграция `003_duels.sql`, `worker.ProcessingVersion = 2`, `store.DuelsSinceVersion = 2`. Номер `004` занят change `add-match-import` (`004_imports.sql`). Для расширения взять следующий свободный номер миграции на момент реализации (`005`, если `add-match-import` применён раньше) и ProcessingVersion выше актуальной (3, если её не поднимали). Сохранить matches.result_version как версию успешного baseline-результата: processed_version последней попытки её не заменяет. Наличие result_version >= DuelsSinceVersion доказывает наличие baseline-дуэлей, но не новых метрик. Миграция не заполняет расширенные группы нулями или complete. Три endpoint-а personal-duels сохраняются.

Полный успешный пересчёт заменяет согласованный набор baseline, дуэлей, новых групп и журнала одной транзакцией. Частичный пересчёт расширения не обновляет result_version baseline и не удаляет match_duels. Сохранённые версии отражают реально обновлённые группы. Старый бинарь может изменить baseline, оставив расширение устаревшим: после отката либо запрещать такие записи, либо обнаруживать несовместимое поколение и помечать расширение stale/unavailable до выдачи. Простого «старый бинарь запускается» недостаточно для гарантии согласованности; способ защиты проверить до деплоя.

## Risks / Trade-offs

Часть событий содержит nil/неизвестного участника; такие события не приписываются случайному игроку. Отсутствие данных снижает покрытие затронутой метрики. Если неизвестно, кого затронула потеря, нельзя объявлять полноту этой метрики для всей карты.

Клатчи требуют больше состояния, чем текущая модель; флешки и огонь — проверки атрибуции. Предлагается поэтапный выпуск независимых проверенных групп. Производительность оценить на типичном вечере и длинной демке с overtime; конкретный бюджет памяти/времени определить по baseline, а не выдумывать в документе.

## Migration Plan

1. Согласовать определения и контрольные примеры; проверить извлечение на локальных копиях демок.
2. Добавить модель, расчёты, миграцию и статусы доступности; сохранить совместимость существующих ответов.
3. Пересчитать контрольный набор и сравнить базовые показатели до/после.
4. Разрешить пересчёт истории и API только для проверенных метрик; неподтверждённые оставить unavailable.
5. При откате не удалять демки/старые результаты; возможность отката схемы и порядок деплоя согласовать до миграции.
