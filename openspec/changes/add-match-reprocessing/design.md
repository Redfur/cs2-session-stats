# Design

## Context

Мотивация — в proposal.md, требования — в specs/. Что есть сейчас:
- `matches.status` (`pending`/`parsing`/`done`/`failed`) одновременно описывает и очередь, и наличие данных: итоги сессии (`store.SessionPlayers`) берут только `status = 'done'`.
- `store.SaveMatchResult` уже атомарно заменяет игроков матча в транзакции, а `store.FailMatch` меняет только статус и ошибку, не трогая `match_players`. Поэтому прежний результат сохраняется при ошибке без доработок.
- Демки лежат в `ingest.LocalStorage` по sha256. Воркер открывает их через `DemoOpener`; если файла нет, `Open` возвращает ошибку `os.ErrNotExist`.
- Очередь: `ClaimNextPending` берёт `ORDER BY id`. `Worker.Run` при старте вызывает `ResetParsing`, затем опрашивает очередь по сигналу `Wake` или раз в 30 с.

## Goals / Non-Goals

**Goals:**
- Разделить «состояние обработки» и «наличие результата», не ломая существующий API и статусы.
- Один путь обработки для первой загрузки и для пересчёта: та же очередь и тот же воркер.
- CLI работает с базой напрямую, без HTTP и без отдельной авторизации.

**Non-Goals:**
- История результатов разных версий: храним только последний успешный.
- Отмена пересчёта, прогресс в процентах.
- Мгновенная реакция сервиса на CLI: допускается задержка до интервала опроса (30 с).

## Decisions

### 1. Две новые колонки вместо новых статусов
Миграция `002_reprocessing.sql`:
- `has_result INTEGER NOT NULL DEFAULT 0` — у матча есть посчитанный результат в `match_players`;
- `processed_version INTEGER NOT NULL DEFAULT 0` — версия обработки последней завершённой попытки (успешной или нет).

Для существующих строк миграция ставит `has_result = (status = 'done')`, а `processed_version = 1` для `done` и `failed`: они обработаны кодом, который и станет версией 1.

`status` сохраняет прежний смысл (состояние последней или текущей обработки). Комбинации:

| status | has_result | Что видит пользователь |
|---|---|---|
| pending/parsing | 0 | «в очереди / обрабатывается», данных нет |
| pending/parsing | 1 | прежние данные + «пересчитывается» |
| done | 1 | данные |
| failed | 0 | ошибка вместо данных |
| failed | 1 | прежние данные + ошибка пересчёта |

- Альтернатива: отдельные статусы `reparse_pending` и `reparse_failed`. Это размножает ветки в очереди, API и UI, а информация та же.
- Альтернатива: `result_version` вместо `has_result`. Отличить «пересчёт упал на новой версии» от «не пересчитывался» можно и по `processed_version`, так что одной версии достаточно.

### 2. Версия обработки — константа в `internal/worker`
`worker.ProcessingVersion = 1`. Её поднимают при изменениях в `internal/parser` или `internal/stats`, которые меняют сохраняемые счётчики. Правило фиксируется в README и в комментарии к константе.
Изменение только формул производных показателей (rating, ADR и т.п.) версию не требует: они считаются из счётчиков при чтении.
Константа живёт в воркере, потому что версия описывает весь конвейер «демка → счётчики», а не только парсер.

### 3. Хранилище
- `SaveMatchResult(ctx, id, result, version)` — дополнительно ставит `has_result = 1` и `processed_version`.
- `FailMatch(ctx, id, msg, version)` — ставит `processed_version`, `has_result` не меняет.
- `ClaimNextPending` — `ORDER BY has_result, id`: матчи без результата (новые загрузки) идут первыми.
- `RequeueMatch(ctx, id) (Match, error)` — `UPDATE ... SET status='pending', error='' WHERE id=? AND status NOT IN ('pending','parsing')`. Затем возвращается актуальная строка; если строки нет, возвращается `ErrNotFound`. Повторный запрос для уже стоящего в очереди матча идемпотентен.
- `RequeueSession(ctx, sessionID) (int64, error)` и `RequeueAll(ctx) (int64, error)` — то же условие, возвращают число затронутых строк.
- `RequeueOutdated(ctx, version) (int64, error)` — `WHERE processed_version < ? AND status NOT IN ('pending','parsing')`.
  Новые матчи имеют `processed_version = 0`, но они уже `pending`, поэтому под условие не попадают.
- `SessionPlayers` фильтрует по `m.has_result = 1` вместо `status = 'done'`. Ник «из последнего матча» берётся по тому же условию.

### 4. Воркер
- `Run`: после `ResetParsing` вызывается `RequeueOutdated(ProcessingVersion)`, число поставленных матчей пишется в лог.
- `process` передаёт `ProcessingVersion` в `SaveMatchResult` и `FailMatch`.
- Отсутствующая демка: `errors.Is(err, fs.ErrNotExist)` превращается в ошибку «исходная демка не найдена».
- Логика «остановка сервиса не помечает матч failed» не меняется.

### 5. API
- `POST /api/matches/{id}/reparse` → `202` и актуальный матч; `404`, если матч не найден. После постановки вызывается `Wake()`.
- `POST /api/sessions/{id}/reparse` → `202` и `{"queued": N}`; `404` для неизвестной сессии.
- В JSON матча добавляются поля `hasResult` и `processedVersion`. `GET /api/matches/{id}` отдаёт игроков при `hasResult`, независимо от статуса; сейчас они и так отдаются из `match_players`.

### 6. CLI: `cs2stats reparse --match ID | --session ID | --all`
Разбор флагов через `flag.FlagSet`. Проверяется, что задан ровно один параметр. Команда открывает БД по `DATA_DIR`, вызывает соответствующий `Requeue*` и печатает «поставлено в очередь: N».
Сигнал работающему сервису не передаётся: он подберёт матчи при ближайшем опросе очереди (≤ 30 с). При старте сервиса `pending`-матчи обрабатываются как обычно.
В Docker команда выполняется так: `docker compose exec cs2stats /cs2stats reparse --all`. Контейнер работает с тем же `DATA_DIR`.
- Альтернатива: CLI вызывает HTTP API. Это потребовало бы адрес сервиса и сломалось бы, когда сервис не запущен.

### 7. Фронтенд
- Тип `Match` получает поля `hasResult` и `processedVersion`. Общая функция `matchStatusLabel(m)` даёт тексты: «в очереди», «обрабатывается», «пересчёт в очереди», «пересчитывается», «готово», «ошибка», «ошибка пересчёта».
- Страница матча:
  - кнопка «Пересчитать», неактивная при `pending`/`parsing`;
  - scoreboard показывается при `hasResult`;
  - пока матч в очереди или обработке, страница опрашивает API раз в 3 с, как страница сессии.
- Страница сессии: кнопка «Пересчитать все матчи» с подтверждением `confirm()`; после ответа данные перезагружаются, и включается существующий опрос.
  Столбец «Счёт» показывается при `hasResult`.

## Risks / Trade-offs

- [Забыли поднять версию после изменения парсера] → старые матчи не пересчитаются автоматически. Остаются ручные способы, а правило записано в README и в комментарии к константе.
- [Массовый пересчёт после поднятия версии занимает время: ~3 с на демку] → он идёт в фоне, новые загрузки идут первыми, старые данные видны до конца пересчёта.
- [Демка удалена из хранилища, например после будущей политики хранения] → пересчёт падает с понятной ошибкой, прежний результат сохраняется.
- [CLI и сервис пишут в одну SQLite из разных процессов] → WAL, `busy_timeout` и `_txlock=immediate` уже настроены. Запросы CLI короткие.
- [Неудачный пересчёт оставляет `status = failed` у матча с данными] → UI различает этот случай по `hasResult` и показывает «ошибка пересчёта», а не прячет данные.

## Migration Plan

1. Миграция `002` применяется при старте, существующие `done`/`failed` матчи получают `processed_version = 1`.
2. `ProcessingVersion = 1`, поэтому после обновления массового пересчёта нет.
3. Откат: старый бинарь игнорирует новые колонки. Единственное отличие — `SessionPlayers` снова будет брать только `done`.
