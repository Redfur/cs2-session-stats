# Design

## Context

Проект пустой. Мотивация описана в proposal.md, требования — в specs/. Ограничения, которые определяют решения:
- В демке CS2 нет даты матча, поэтому сессию создаёт пользователь (см. `game-sessions`).
- Демка весит 100–400 МБ, парсинг занимает секунды и до ~1 ГБ RAM. Нагрузка — единицы демок за вечер от одной компании.
- Хостинг не выбран: всё должно запускаться одной командой `docker compose up` и одинаково локально и на VPS.
- Фронт — прототип, без UI-кита.

## Goals / Non-Goals

**Goals:**
- Один процесс и один контейнер: проще деплой и отладка.
- Статистика считается из сохранённых в БД агрегатов, без повторного парсинга при каждом просмотре.
- Код расчёта метрик отделён от парсера и покрыт unit-тестами на синтетических событиях.

**Non-Goals:**
- Горизонтальное масштабирование, распределённая очередь.
- Хранение сырых событий (позиций, тиков) для будущих фич: добавим отдельным change, когда понадобится. Исходные демки сохраняются, поэтому их можно перепарсить.
- Авторизация: сервис рассчитан на закрытое использование в компании.

## Decisions

### 1. Один Go-бинарь: API + воркер + статика фронта
`cmd/cs2stats` поднимает HTTP-сервер (`net/http` со стандартным `ServeMux` и паттернами `GET /api/sessions/{id}`), воркер парсинга и раздаёт собранный фронт через `embed`: Vite собирает в `internal/webui/dist`, встраивание включается build tag `embedweb` (в Docker), без тега статика читается с диска — так `go build`/`go test` работают без сборки фронта.
- Альтернатива: отдельные сервисы api/worker + Redis-очередь. Избыточно для такой нагрузки.

### 2. Очередь — таблица `matches` + один воркер-горутина
Воркер берёт матчи в статусе `pending` по одному: `UPDATE ... SET status='parsing' ... RETURNING`, разбуживается через канал после загрузки. При старте все `parsing` сбрасываются в `pending`, это закрывает сценарий перезапуска.
Параллельность = 1: ограничивает пиковую RAM; при необходимости увеличим через настройку.
- Альтернатива: канал в памяти без статуса в БД. Теряет задачи при рестарте.

### 3. SQLite (`modernc.org/sqlite`, без CGO), WAL-режим
Схема (упрощённо):
- `sessions(id, date, title, created_at)`
- `matches(id, session_id, ordinal, sha256 UNIQUE, original_name, status, error, map, rounds, score_a, score_b, created_at, parsed_at)`. Путь к файлу не хранится: хранилище демок адресует их по sha256.
- `match_players(match_id, steam_id, name, team ('A'|'B'), result, rounds, kills, deaths, assists, hs_kills, damage, kast_rounds, k1..k5, opening_kills, opening_deaths, PRIMARY KEY(match_id, steam_id))`. Rating не хранится: он считается из счётчиков (k1 нужен для формулы).

В `match_players` храним **сырые счётчики**, а не проценты. Тогда агрегаты сессии (ADR, KAST, HS%, взвешенный rating) корректно считаются суммами в SQL или Go.
Миграции — SQL-файлы через `embed`, применяются при старте, версия хранится в `PRAGMA user_version`. Отдельная библиотека миграций не нужна.
- Альтернатива: Postgres. Лишний контейнер на этапе MVP; переход возможен отдельным change.

### 4. Парсер: `github.com/markus-wa/demoinfocs-golang/v5`
Актуальная стабильная версия v5.2.0; v6 пока в alpha. Пакет `internal/parser` подписывается на события (`MatchStart`, `RoundStart`, `RoundEnd`, `Kill`, `PlayerHurt`), отбрасывает всё до последнего `MatchStart`, то есть разминку, и превращает их в доменные структуры без зависимостей от demoinfocs:
`Match{Map, Rounds []Round, Players, ScoreA, ScoreB}`, `Round{Kills []Kill, Damages []Damage, Survivors}`.
Команда A — та, что начала матч за CT; после смены сторон её текущая сторона определяется по большинству её известных игроков на старте раунда. Счёт считается по победителям раундов. От семантики `TeamState` не зависим, поэтому смена сторон не ломает группировку. Если в демке нет RoundEnd последнего раунда, победитель восстанавливается по итоговому счёту сторон.
- Альтернатива: `demoparser2` (Rust) через Python. Другой язык в стеке.

### 5. Расчёт статистики — чистые функции в `internal/stats`
`stats.Compute(match parser.Match) []PlayerStats`: на вход доменные события, на выход счётчики. Без I/O, поэтому легко тестировать на синтетических раундах.
Константы: окно размена 5 с. Rating 1.0: `(K/R/0.679 + 0.7·(R−D)/R/0.317 + (1K+4·2K+9·3K+16·4K+25·5K)/R/1.277) / 2.7`.
Rating за сессию — среднее, взвешенное по раундам.

### 6. Загрузка: потоковая запись с хешированием
`POST /api/sessions/{id}/demos` принимает multipart. Каждый файл потоково распаковывается: gzip/bzip2 из stdlib, zstd из `github.com/klauspost/compress/zstd`, zip из stdlib. Распакованный поток пишется во временный файл через `io.MultiWriter` вместе с SHA-256 и `io.LimitReader` по лимиту. Потом файл переименовывается в `/data/demos/<sha256>.dem`. Демка целиком в память не грузится.
Zip читается из временного файла, потому что `archive/zip` требует `ReaderAt`.
Порядок матчей: `ordinal = max(ordinal в сессии) + индекс файла` в одной транзакции.
- Лимит тела запроса снимаем (`MaxBytesReader` по сумме лимитов), таймауты сервера увеличены для больших загрузок.

### 7. API (JSON)
- `GET /api/sessions` → список `{id, date, title, matchCount}`
- `POST /api/sessions` `{date?, title?}` → сессия
- `GET /api/sessions/{id}` → сессия + матчи + сводная таблица игроков
- `POST /api/sessions/{id}/demos` (multipart `files`) → `[{fileName, status: accepted|duplicate|error, matchId?, sessionId?, error?}]`
- `GET /api/matches/{id}` → матч + игроки

Ошибки возвращаются как `{error: string}` с соответствующим HTTP-кодом.

### 8. Фронт: Vite + React + TypeScript + react-router
Три маршрута: `/`, `/sessions/:id`, `/matches/:id`. Данные загружаются через `fetch` и `useEffect`, стили — минимальный CSS.
Страница сессии опрашивает `GET /api/sessions/{id}` раз в 3 с, пока есть матчи `pending`/`parsing`.
В dev-режиме Vite проксирует `/api` на Go-сервер; в prod Go раздаёт встроенную статику.
- Альтернатива: TanStack Query. Отложено, пока хватает простого fetch.

### 9. Docker
Multi-stage `Dockerfile`: `node` собирает `web/dist` → `golang` собирает статический бинарь (`CGO_ENABLED=0`) → `gcr.io/distroless/static` или `alpine`.
`docker-compose.yml`: один сервис, volume `./data:/data`, порт 8080.

### 10. Хранение исходных демок
На время активной разработки демки хранятся на локальном диске (`/data/demos`) без срока хранения. Это нужно, чтобы перепарсить историю после исправлений парсера и добавления новых метрик.
Работа с файлами демок идёт через небольшой интерфейс в `internal/ingest` (`Save`, `Open`, `Delete`) с реализацией на локальной ФС. Позже его можно заменить на S3/MinIO без изменений в воркере и API.
- Решение для публичного деплоя на VPS отложено: внешнее хранилище (S3/MinIO) или удаление демки после парсинга. Принимается отдельным change перед деплоем.

## Risks / Trade-offs

- [Обновление CS2 ломает формат демок] → храним исходные демки. После обновления demoinfocs статистику можно пересчитать: команда reparse — кандидат на следующий change.
- [Демки FastCup/Cybershoke могут отличаться: нестандартный старт матча, knife-раунд, рестарты] → берём раунды после последнего `MatchStart`. Golden-проверка на реальных демках обеих платформ входит в задачи; найденные отличия чиним в парсере.
- [Rating 1.0 устарел относительно HLTV 2.0/3.0] → для сравнения внутри компании достаточно; формулу можно заменить без перепарсинга, потому что в БД лежат сырые счётчики.
- [Большие загрузки через браузер при медленном канале] → для MVP приемлемо. Загрузку по ссылке сделаем отдельным change.
- [Нет авторизации] → не выставлять сервис в интернет без reverse proxy с basic auth. Это нужно отметить в README.
- [Запись в одну базу SQLite из двух горутин: API и воркер] → WAL + `busy_timeout`, запись короткими транзакциями.

## Migration Plan

Первый релиз, миграций данных нет. Откат — остановить контейнер; данные в `./data` переживают пересборку.

## Open Questions

- Политика хранения демок для публичного деплоя (S3/MinIO или не хранить). Решается перед деплоем на VPS отдельным change, на MVP не влияет.
