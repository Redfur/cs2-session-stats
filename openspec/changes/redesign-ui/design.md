# Design

## Context

Фронтенд (`web/`) — Vite 8 + React 19 + react-router 8. Пять страниц и 404, около 1100 строк TSX, стили —
11 строк в `web/src/index.css`, UI-зависимостей нет. Фильтры страниц игроков уже хранятся в адресе через
`useSearchParams`, загрузка демок уже идёт через XHR (`api.uploadDemos`), но все файлы уходят одним запросом.

Источник дизайна — артефакт Claude Design https://claude.ai/artifact/RyiK38Ld5u2q9uQMxYhe6h: страница
«Дизайн-система» (10 досок) и «Экраны» (12 досок). Снимок файлов `project/*.dc.html` и `app.css` лежит в
`data/design-input/design/` (вне git) для справки при реализации. Готовый блок `@theme` для Tailwind v4 —
на доске «02 Отступы, радиусы, тени» (`Scale.dc.html`).

Бэкенд: `GET /api/sessions` → `store.ListSessions` возвращает `id, date, title, createdAt, matchCount`.
Итоги сессии считаются в `store.SessionPlayers` (тот же код, что и общая таблица игроков),
производные показатели — в `api.totalsView`.

## Goals / Non-Goals

**Goals:**
- Разметка и стили повторяют макеты. Расхождения допустимы там, где макет нарушает доступность или
  противоречит спекам.
- Компоненты переиспользуются: новые экраны и будущие графики собираются из `components/ui` без новых стилей.
- Минимум зависимостей сверх выбранных пользователем: Tailwind, Headless UI, fontsource, иконки Lucide.

**Non-Goals:**
- Светлая тема, графики, аватары, авторизация.
- Изменение схемы БД, `ProcessingVersion`, формул показателей.
- Общий state-менеджер или библиотека запросов: страницы по-прежнему грузят данные сами.

## Decisions

### Стили: Tailwind v4 через `@tailwindcss/vite`, токены из макета
`web/src/index.css` = `@import "tailwindcss"` + `@fontsource-variable/manrope` + `@fontsource-variable/jetbrains-mono`
+ блок `@theme` из макета без изменений имён (`--color-fg`, `--color-metric-good`, `--text-page` …) + `@layer base`.
Повторяющиеся сочетания (кнопка, бейдж, ячейка таблицы) оформляются React-компонентами, а не `@apply`.
Так у каждого класса один источник правды.
- Альтернатива — CSS Modules. Отклонена: пользователь выбрал Tailwind, и макет уже выражен его токенами.
- Плагин Vite, а не PostCSS: это рекомендуемый путь для v4, peer-зависимость допускает Vite 8.

### Иконки: `lucide-react`
Макет использует Lucide. Пакет tree-shakable, в бандл попадают только импортированные иконки.
Альтернатива — копировать SVG вручную. Отклонена: иконок около 25, ручные копии сложнее поддерживать.

### Компоненты `web/src/components/ui/`
`Layout` (шапка 56 px, `NavLink` с `aria-current`; «Сессии» активна и на `/sessions/*`, `/matches/*`),
`PageHeader` (назад, заголовок, мета, действия), `Card`, `Button` (primary / secondary / ghost / danger /
danger-quiet, размеры md/sm/xs, icon, loading), `Field`/`Input`, `Checkbox`, `Segment` (Headless UI `RadioGroup`),
`StatusBadge`, `OutcomeBadge`, `Score`, `ScoreBoard`, `MetricValue`, `StatTable`, `ConfirmDialog`, `FormDialog`,
`DropZone`, `UploadList`, `EmptyState`, `Alert` (info / error), `StatTile`.
Компоненты не знают об API, они получают данные пропсами. Связка с API — на страницах и в хуках.

### Таблица статистики — настоящий `<table>`
Макет сделан на grid из `div`, в коде — `<table>` для скринридеров. Заголовок — `<button>` внутри `<th aria-sort>`.
Закреплённая колонка: `position: sticky; left: 0` с непрозрачным фоном: `surface`, при выделении `#272521`
(как в макете). Обёртка — `overflow-x: auto` внутри карточки. Описание колонок — массив
`{ key, label, numeric, value(row), render?, metric?, secondary? }`. Одно описание колонок игрока используется в
итогах сессии, таблицах матча, общей таблице и итогах профиля.
- Сортировка на клиенте: данных максимум десятки строк. Сравнение стабильное. При равенстве — исходный
  порядок (сервер уже отдаёт по rating).

### Сортировка в адресе: хук `useSort(param, columns, defaultSort)`
Значение — `<колонка>` (направление по умолчанию для колонки) или `<колонка>.asc` / `<колонка>.desc`. Ключи:
`sort` — главная таблица страницы (итоги сессии, обе таблицы матча вместе, общая таблица игроков);
на профиле `ss` (по сессиям), `sm` (по картам), `sx` (матчи). Значение по умолчанию в адрес не пишется.
Неизвестная колонка игнорируется. Обновление адреса — через `setSearchParams(..., { replace: true })`,
чтобы клики по сортировке не засоряли историю. Существующие параметры фильтров
(`from, to, session, player, together, minMatches`) не пересекаются с новыми ключами.

### Шкала метрик: `web/src/metrics.ts`
`metricLevel(metric, value): 'good' | 'mid' | 'bad' | null` с порогами из спеки `web-ui`. Сравнивается
**отображаемое округлённое значение** (rating и K/D до 2 знаков, ADR до 1, KAST до целого процента), иначе
1.1501 показывается как «1.15», но окрашивается в «хорошо». Граница включается в «средне».

### Диалоги: `ConfirmDialog` на Headless UI `Dialog`
Пропсы: `title`, `description`, `confirmLabel`, `tone: 'danger' | 'normal'`, `onConfirm: () => Promise<void>`.
Пока промис выполняется, кнопка в состоянии loading, а закрытие (Esc, клик по фону) заблокировано. При ошибке
текст показывается над кнопками, диалог остаётся открытым. Для `danger` `initialFocus` стоит на «Отмена».
`FormDialog` для «Новой сессии» — тот же каркас с формой.

### Загрузка: очередь на клиенте, один файл — один запрос
`api.uploadDemo(sessionId, file, onProgress, signal)` отправляет один файл. При `signal.abort()` вызывается
`xhr.abort()`, промис отклоняется с `AbortError`. Хук `useUploadQueue(sessionId, onAccepted)` хранит
элементы `{ id, file, state: queued|sending|accepted|duplicate|error|cancelled, loaded, total, result, eta }`
и отправляет их строго по одному. Это сохраняет порядок `ordinal` (спека `demo-ingestion`). После каждого
принятого файла вызывается `onAccepted` → `load()` страницы. Оценка времени — по скорости,
сглаженной экспонентой за последние секунды, и показывается после 2 с отправки.
Проверка формата на клиенте — по суффиксу без учёта регистра (`.dem`, `.dem.gz`, `.dem.bz2`, `.dem.zst`, `.zip`),
как `ingest.detectFormat`. Сервер по-прежнему проверяет сам.
- Отмена файла во время отправки: обрыв multipart-потока даёт ошибку чтения части, `Ingest` возвращает
  `Failed`, удаляет временный файл, матч не создаётся. Проверяется E2E.
- Альтернатива — один запрос со всеми файлами (как сейчас). Отклонена: нет прогресса и отмены по файлу.

### Перестановка матчей: свой drag на Pointer Events
Ручка в строке — `<button>`. `pointerdown` захватывает указатель, строка «поднимается», между строками
рисуется линия вставки, на исходном месте строка остаётся с прозрачностью 40%. `pointerup` сразу
переставляет локально и отправляет `PUT /order` с полным списком. При ошибке страница показывает ошибку и
перезагружает сессию. С клавиатуры: на ручке ↑/↓ сдвигают на одну позицию, фокус остаётся на ручке
перемещённого матча, изменение объявляется через `aria-live`.
- Альтернатива — `@dnd-kit/sortable`. Отклонена: его клавиатурная модель «пробел — взять, стрелки,
  пробел — положить» не совпадает с макетом (стрелки сразу), а для одного списка из 5–10 строк
  зависимость избыточна. Нативный HTML5 DnD отклонён: не работает на тач-экранах.

### Правка сессии на месте
`InlineEdit` для названия и для даты. Каждое поле отправляет `PATCH` с текущим значением второго поля:
API принимает дату и название вместе. Пока правится одно поле, второй карандаш скрыт.

### Плашка пересчёта
Сервер не знает о «пачке» пересчёта, поэтому прогресс считает страница. Множество `reparseIds` —
id матчей, которые хоть раз были замечены с результатом в статусе `pending`/`parsing`, начиная с момента,
когда таких не было. N = размер множества, готово = N − текущие пересчитываемые. Когда пересчитываемых
не осталось, множество очищается и плашка скрывается. Если страница открыта посреди пересчёта, N считается
с момента открытия. Для одной вкладки этого достаточно.

### Страница матча: название сессии и соседи
После загрузки матча страница запрашивает `GET /api/sessions/{sessionId}` и берёт название и список матчей
(номер, id) для «N из M» и стрелок. Бэкенд не меняется. Второй запрос дешёвый.
- Альтернатива — добавить поля в ответ матча. Отклонена: лишнее изменение API ради одной страницы.

### Сводка сессий в списке: расширение `GET /api/sessions`
`SessionSummary` получает поля:
- `maps: string[]` — карты матчей с результатом в порядке `ordinal`, без повторов. Отдельный запрос
  `SELECT session_id, map FROM matches WHERE has_result = 1 ORDER BY session_id, ordinal`, дедупликация в Go.
- `failedCount: number` — `sum(m.status = 'failed')` в основном запросе.
- `best?: { steamId, name, rating }` — для каждой сессии с результатами вызывается `SessionPlayers`, и через
  `totalsView` выбирается максимум rating (при равенстве — больше раундов, затем ник). Код и правила ника те
  же, что на странице сессии, поэтому значения совпадают.
Поиск и группировка по месяцам — на клиенте. Названия месяцев берутся из `Intl.DateTimeFormat('ru', { month: 'long' })`
с заглавной буквы.
- Альтернатива для `best` — один агрегирующий запрос с `GROUP BY session_id, steam_id`. Отклонена пока: пришлось
  бы дублировать вычисление ника и rating. Запрос на сессию дёшев при десятках-сотнях сессий
  (см. Risks).

### Фильтры игроков
`PeriodFilter` переходит на `Segment` «Даты / Сессии». В режиме сессий на странице игроков — список чекбоксов в
боковой панели (ширина 280). На профиле — кнопка «Выбрать сессии · N» с Headless UI `Popover`. Логика
параметров адреса не меняется.

## Risks / Trade-offs

- [Preflight Tailwind сбрасывает стили браузера, и в промежуточном коммите старые страницы выглядят хуже]
  → коммит с основой и коммит со страницами идут подряд в одной ветке. Каждый собирается и проходит тесты.
- [`best` через `SessionPlayers` даёт по запросу на каждую сессию] → при сотнях сессий это миллисекунды на
  SQLite. Если список станет медленным, перейти на агрегирующий запрос отдельным change.
- [Свой drag&drop — больше кода и краевых случаев: скролл во время перетаскивания, отмена по Esc,
  мультитач] → поддерживаются мышь, тач и клавиатура. Esc во время перетаскивания отменяет его. Автоскролл
  не делаем: список матчей короткий.
- [Плашка пересчёта не видит пачку, запущенную в другой вкладке до открытия страницы] → считает от момента
  открытия. Это допустимо для одного пользователя.
- [Размер бандла: шрифты и Headless UI] → вариативные woff2 с подмножествами latin и cyrillic, примерно
  по 50–100 КБ. Бинарь со встроенным фронтом растёт незначительно.
- [Сравнение метрик по округлённому значению расходится с «сырым» на сотые] → так и задумано: цвет совпадает
  с тем, что видит пользователь.

## Migration Plan

Миграций БД нет. Новые поля API только добавляются. Порядок коммитов: бэкенд сводки сессий → основа фронтенда
(зависимости, токены, компоненты) → страницы и UX → исправления по итогам проверки → архивация OpenSpec.
Откат — revert коммитов фронтенда. Бэкенд-поля безвредны для старого фронта.
