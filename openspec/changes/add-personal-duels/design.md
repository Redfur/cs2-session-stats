# Design

## Context

`parser.Match` уже содержит `Round.Kills` с участниками и команды игроков матча. `stats.Compute` отбирает убийства противников правилом `isEnemyKill`: оба игрока в матче, разные команды, не суицид. Окна раундов, рестарты FastCup и конец матча уже учтены парсером, `internal/parser` менять не нужно.

Воркер сохраняет результат матча через `store.SaveMatchResult` одной транзакцией. `FailMatch` прежний результат не трогает. `processed_version` обновляется и при неудачной попытке, поэтому по нему нельзя понять, какой версией получен *сохранённый* результат.

Профиль игрока (`GET /api/players/{steamId}`) уже разбирает фильтр периода (`parsePeriod`) и берёт ник из последнего матча без учёта периода.

## Goals / Non-Goals

**Goals:** сырые парные счётчики в БД, три представления (матрица матча, матрица сессии, два показателя профиля), безопасный переход старых матчей через пересчёт.

**Non-Goals:** общий журнал событий матча, детектор перехода игрока в другую команду посреди карты, изменения существующих формул (ADR, KAST, rating), подгонка под табло FastCup.

## Decisions

### 1. Расчёт — в `internal/stats` на тех же enemy kills

`stats.Compute` (или соседняя функция того же пакета) дополнительно возвращает `[]Duel{Killer, Victim, Kills}` для всех пар соперников матча, включая нули: 5×5 даёт 50 направленных пар. Используется то же `isEnemyKill`, поэтому сумма убийств игрока по дуэлям совпадает с его K. Это инвариант для тестов. Отдельный проход по раундам с собственным фильтром отвергнут: правила K и дуэлей могли бы разойтись.

### 2. Хранение

Миграция `003_duels.sql`:
- `match_duels(match_id REFERENCES matches(id) ON DELETE CASCADE, killer_id, victim_id, kills, PRIMARY KEY(match_id, killer_id, victim_id))`. Хранятся только убийства, смерти D(A,B) — это строка K(B,A). FK в БД включены (`foreign_keys(1)`), поэтому удаление матча удаляет его дуэли.
- `matches.result_version INTEGER NOT NULL DEFAULT 0` — версия обработки, которой получен сохранённый результат. Пишется только в `SaveMatchResult`. Заполнение: `result_version = 1` там, где `has_result = 1`.

`SaveMatchResult` в одной транзакции удаляет и вставляет `match_players` и `match_duels`, ставит `result_version`. Если матч удалён во время обработки, `UPDATE` не находит строку, возвращает `ErrNotFound`, и транзакция откатывается. Это уже работает и для дуэлей отдельной защиты не требует.

**Матч с посчитанными дуэлями** — `has_result = 1 AND result_version >= 2`. Отдельная версия дуэлей отвергнута: одна `ProcessingVersion` проще, а `result_version` закрывает разницу между «посчитано» и «пытались посчитать».

### 3. Версия обработки

`worker.ProcessingVersion = 2`. При старте `RequeueOutdated` ставит старые матчи в очередь. Новые загрузки обрабатываются раньше (`ClaimNextPending` по `has_result, id`). Пока матч не пересчитан, его основной результат виден, а дуэли считаются не посчитанными.

### 4. API

Отдельные endpoint'ы: основные страницы не ждут дуэлей, и фронтенд подгружает блок отдельно.

- `GET /api/matches/{id}/duels` → `{ status, players: [{steamId, name, team}], cells: [{killerId, victimId, kills, deaths, share}] }`. `status`: `complete` или `unavailable` (дуэли не посчитаны или у матча нет результата).
- `GET /api/sessions/{id}/duels` → `{ status, eligibleMatches, coveredMatches, uncoveredMatches: [{id, ordinal}], players: [...], cells: [{killerId, victimId, kills, deaths, share, maps}] }`. `uncoveredMatches` — матчи с результатом без дуэлей: нужны для строки «Матчи #4 и #5…» и кнопки «Пересчитать их», которая вызывает существующий `POST /api/matches/{id}/reparse` для каждого. Ячейки есть только у пар, которые хотя бы раз были соперниками. Порядок `players` — как в итогах сессии (rating по убыванию).
- `GET /api/players/{steamId}/duels?from&to|session` → `{ status, eligibleMatches, coveredMatches, coveredSessions, mostKilled: [...], mostKilledBy: [...], opponents: [{steamId, name, kills, deaths, share, maps}] }`. Фильтр — тот же `parsePeriod`, неизвестный игрок — 404, как у профиля.

`status` для сессии и профиля: `no_matches` (нет матчей с результатом), `unavailable` (ни у одного нет дуэлей), `partial` (`coveredMatches < eligibleMatches`), `complete`. SteamID — строки. `share` — число 0..1 или `null` при K+D=0, считается при чтении из сумм, как прочие производные показатели. `opponents` нужен для проверок и будущих блоков, интерфейс в этом change его не выводит.

Ник соперника — из его последнего матча без учёта периода, как в заголовке профиля. Последний матч определяется так же, как в `player-stats` («Ник игрока за период»).

### 5. Интерфейс

Источник — макеты Claude Design `DuelMatrix`, `DuelMobile`, `S02`/`S02b`, `S07`, `S12` (снимок в `data/design-input/design/`).

- **Токены.** `--color-duel-1…5` (`#F25F5C`, `#F5A65A`, `#6F757B`, `#C9D857`, `#41C463`) добавляются в `@theme`. Это отдельная расходящаяся шкала доли, шкала метрик для неё не используется.
- **Компонент `DuelMatrix`** в `web/src/components/ui`: CSS grid с колонкой ников (168 px, на узком экране 112 px) и столбцами от 84 px (72 px). Колонка ников `sticky`, на мобильном с тенью и затуханием у правого края. Обёртка прокрутки `relative`, как у таблиц. Необязательная полоса команд для матча. Ячейка: «K · p%» нейтральными цифрами и полоска, у которой подложка тонирована ступенью, сплошная часть — доля, риска — 50%. Наведение и касание подсвечивают строку и столбец и открывают подсказку. Для экранного диктора в ячейке есть текст `sr-only` с полным счётом.
- **Ступень и округление** — чистые функции рядом с `metrics.ts`. `pct(k, d)` округляет, но не даёт 50 при k ≠ d. `level(k, d)`: ≤25 → 1, <45 → 2, ≤55 → 3, <75 → 4, иначе 5. При k + d < 4 ступень зажимается в 2…4. Отдельного тест-раннера для фронта нет, поэтому значения на границах ступеней проверяются в headless-браузере на тестовых данных.
- **Матч:** блок после таблиц команд, игроки в порядке scoreboard (команда A, затем B). Состояние «Дуэли ещё не посчитаны» с кнопкой «Пересчитать матч».
- **Сессия:** блок между «Итоги сессии» и «Матчи», порядок игроков из итогов сессии. Свёрнутость — в `localStorage` с try/catch, общая для всех сессий. Частичное покрытие: нейтральный бейдж и строка с номерами матчей и кнопкой «Пересчитать их».
- **Профиль:** блок «Соперники» между разбивками («По сессиям», «По картам») и «Матчи». Две колонки, на узком экране одна под другой. Строка: ник (`plink`, обрезка), счёт с выделенным значимым числом (`hi`/`lo`), «на N картах». Над списком «двое/трое поровну».
- **Загрузка и ошибка** — общие для трёх блоков: скелетон и `alert-error` с «Повторить», независимо от основного запроса страницы.

## Risks / Trade-offs

- [Переход игрока в другую команду посреди карты] → Парсер закрепляет команду на весь матч, поэтому дуэли такого игрока будут неточными. Это известное ограничение, как и ADR вышедшего игрока: записать его в CLAUDE.md и README.
- [Расхождения с FastCup] → Сверить все пары на контрольной демке 27802385 со страницей https://cs2.fastcup.net/matches/27802385/stats/duels. Расхождения объяснять конкретными событиями и правилами, под табло не подгонять.
- [Один матч даёт формальный максимум в профиле] → Показывать число карт против, чтобы был виден объём данных.
- [Матрица сессии из 10+ игроков на телефоне] → Прокрутка внутри блока и закреплённая колонка ников по правилам `web-ui`.

## Migration Plan

1. Миграция `003` создаёт таблицу и колонку, заполняет `result_version = 1` у матчей с результатом.
2. Новая версия при старте ставит все матчи на пересчёт. До его окончания API отдаёт `partial`/`unavailable`, а основная статистика не меняется.
3. Откат: старый бинарь запускается на новой схеме, потому что `migrate` пропускает миграции с номером не выше `user_version` и не падает на более новой версии. Таблицу дуэлей он не читает и не обновляет.
