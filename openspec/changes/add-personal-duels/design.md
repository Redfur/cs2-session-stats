# Design

## Context

В `parser.Match` уже есть `Round.Kills` с участниками; `stats.Compute` отбирает enemy kills. Воркер сохраняет только итоговые `PlayerStats`, таблицы событий нет. Предложение ниже относится к самостоятельному demo-источнику сервиса. Проверенные ранее таблицы FastCup/Scope остаются отдельным источником, без неявной подмены.

## Goals / Non-Goals

Цель: воспроизводимые парные счётчики и два компактных вывода. Не цель: общий event store, прогноз силы, миграция всей статистической методики или переработка UI. Новая capability не меняет существующий ADR, KAST или Rating сервиса.

## Decisions

Все физические имена таблиц и полей ниже — предложение для технического ревью; нормативное поведение находится в `specs/personal-duels/spec.md`.

1. Расчёт выполнять рядом с `stats.Compute` на том же наборе `Match.Rounds`, переиспользуя правило enemy kill. Сопоставлять игрока по SteamID64, отдавать ID в JSON строкой. Для стандартных 5×5 достаточно 50 направленных пар на карту; включать пары с известным нулём.
2. Предложение хранения: `match_duels(match_id, player_id, opponent_id, kills)` с уникальным ключом тройки, неотрицательным kills и FK удаления по match_id. Признак готовности и версия дуэлей на матче позволяют отличить отсутствие rows старого формата от нулей. Два направления и отметку готовности писать в одной транзакции с результатом матча. Счёт смерти не дублировать в хранении: это обратная строка.
3. При агрегации брать обе стороны с одного множества покрытых карт. Предполагаемые поля: opponentSteamId, nickname, killsAgainst, deathsTo, eventCount, killShare, opposingMaps, coveredMaps, coveredSessions. `killShare` — число 0..1 либо null. Проверки симметрии: K(A,B)=D(B,A). Основные смерти могут включать мир/суициды и не обязаны совпадать с суммой deathsTo.
4. API-вариант: добавить `personalDuels` в существующий ответ `GET /api/players/{steamId}` с его фильтрами. Возвращать status (`no_matches`, `unavailable`, `partial`, `complete`), числа eligible/covered матчей профиля, список пар и массивы mostKilled/mostKilledBy. `complete` с пустыми максимумами возможен и отличается от `unavailable`. Ник соперника брать по существующей политике ника из последнего матча выборки. Детали endpoint и DTO уточняет разработчик.
5. Интерфейс использует только два массива максимумов; полный список пар нужен для расчётов и проверок, не для обязательной таблицы на экране. Неполнота определяется по всем eligible картам владельца профиля; для каждой пары возвращается своё покрытие. Равенства можно раскрывать в одной компактной строке; не превращать их в несколько крупных карточек.
6. При реализации поднять ProcessingVersion и переобработать старые демки. До успешного пересчёта старые основные метрики остаются доступны, но дуэли неизвестны. Для ранее покрытых матчей сохранять прежние дуэли при очереди/ошибке; новую версию публиковать атомарно. Повторная обработка не создаёт дубликаты. Удаление матча во время обработки не должно воскресить его результат.

## Risks / Trade-offs

- Имеющаяся модель закрепляет команду за игроком внутри матча. Для обычного матча со сменой CT/T это подходит; произвольный переход игрока в другую команду посреди карты требует отдельного решения и не должен молча давать неверные дуэли.
- Наличие завершённых раундов не доказывает целостность всего исходного матча. Полнота обработки дуэлей означает покрытие принятого результата парсера; поддержка обрезанных демок и диагностика целостности согласуются отдельно.
- Один матч может дать формальный максимум. Не добавлять произвольные минимумы или утверждения об устойчивой силе; показывать реальный объём.
- Даты фильтра — даты сессий. Составы пар определяются на карте, даже если в отдельных компаниях пятёрки фиксированы на весь вечер.
- Различия с FastCup записывать по конкретным событиям и правилам. Не подгонять счётчики для совпадения с внешней таблицей.

## Migration Plan

1. Ревьюировать контракт и выбрать API/схему БД.
2. Добавить миграцию и вычисление пар без изменения существующих формул.
3. Поднять версию обработки; проверить сохранение старых результатов и очередь пересчёта.
4. Включить блок после проверки API на complete/partial/unavailable.
5. На общей контрольной демке сверить матрицу с FastCup и зафиксировать объяснённые расхождения. Публично не коммитить демо или персональные данные без отдельной необходимости.

## Open Questions

- Разработчик: отдельная версия дуэлей или общая ProcessingVersion с явным признаком наличия результата?
- Разработчик: поле профиля или отдельный endpoint при оценке объёма ответа?
- Разработчик: как обнаруживать нештатную смену команды внутри карты и неполную запись?
- Совместное ревью: точное место компактного блока в текущем UI и взаимодействие с активным change `redesign-ui`. Этот change не утверждает старые прототипы профиля.
