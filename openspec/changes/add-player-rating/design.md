# Design

## Context

- В БД хранятся только сырые счётчики `stats.Counters` (`match_players`). Производные показатели считаются при чтении в `api.newPlayerView`. `rating` там — `Counters.Rating()` (HLTV 1.0).
- Агрегаты (`store.PlayerTotals`, `PlayerSessions`, `PlayerMaps`, `PlayerMatches`) суммируют счётчики SQL-запросом с `MatchFilter`. Матчей с результатом немного (сотни), игроков — десятки.
- Все входы восстановленной формулы Rating 2.0 (KAST, K, D, A, урон, раунды) уже есть в `Counters`, поэтому миграция и `ProcessingVersion` не нужны.
- Формулы, константы и мотивация — в `openspec/roadmap.md`, раздел 1.1. Ниже только решения по реализации.
- Макеты по брифу `design-brief.md` готовы (артефакт Claude Design, доска «16 Оценка и OVR» и экраны S02d/S02m, S07, S10/S10m, S12/S12b; снимок в `data/design-input/design/`).

## Goals / Non-Goals

**Goals:**
- Одна чистая функция расчёта рейтинга без БД, чтобы её же переиспользовать в 1.2 (история), 1.3 (проверка), 1.4 (подбор составов).
- Бэкенд и API готовы и проверены до макетов. Rating 2.0 сразу заменяет 1.0 в текущих таблицах, это не требует новых макетов.

**Non-Goals:**
- Кэш и хранение OVR: расчёт за один проход по всем матчам на каждый запрос.
- Поправка на силу соперников (γ) и подбор α по прошлым матчам — 1.3. Шаг EMA получает состав матча, но не использует его.
- Разложение изменения OVR по слагаемым формулы — отдельный change.

## Decisions

### 1. Rating 2.0 в `internal/stats`

`Counters.Rating()` теперь возвращает восстановленный Rating 2.0:

```
KPR, DPR, APR — на раунд; KAST — в процентах; ADR — урон за раунд
Impact = 2.13·KPR + 0.42·APR − 0.41
Rating = 0.0073·KAST + 0.3591·KPR − 0.5329·DPR + 0.2372·Impact + 0.0032·ADR + 0.1587
```

При нуле раундов — 0. Старая формула переименовывается в `Counters.Rating1()` и остаётся для сравнения в 1.3, в API не выводится. Так все места, где сейчас `Rating()`, автоматически получают 2.0: таблицы, `pickBest`, сортировка scoreboard и итогов.

Альтернатива — новое имя `Rating2()` и замена вызовов. Отклонена: больше правок без пользы, и 1.0 случайно остаётся где-то в выводе.

Rating 2.0 линеен по величинам «на раунд», поэтому rating по сумме счётчиков — это среднее, взвешенное по раундам. Это сохраняет требования об агрегатах в `game-sessions` и `player-stats`.

Поле JSON `rating` и колонка «Rating» остаются. Меняются подписи «HLTV Rating 1.0» → «HLTV Rating 2.0» (восстановленная формула).

### 2. Шкала `score`

`stats.Score(r float64) float64 = 100 / (1 + exp(−k·(r − r0)))`. Целое при выводе: `math.Round` (`stats.ScorePoints`).

**Выбрано: `k = 3`, `r0 = 0.95`** (задача 1.3, копия рабочей БД на 2026-10-14: 200 строк игрок-матч, 24 игрока). Средний Rating 2.0 компании с весом по раундам — 1.084 (медиана по матчам 1.09, p5 0.46, p95 1.77, максимум 2.22), он получает 60 баллов. Постоянные игроки (10+ матчей, по EMA) — от 38 до 80, лучший матч — 98. Предварительные `k = 4`, `r0 = 0.899` давали среднему игроку 70 и сжимали верх. После этого константы не трогать, иначе съедет вся история; уточнение — только вместе с 1.3.

Средние всегда считаются по Rating 2.0 и только потом переводятся в баллы.

### 3. Пакет `internal/rating`

Чистая функция без БД:

```go
type MatchRow struct {   // один игрок в одном матче, в порядке игры
    MatchID, SessionID int64
    SteamID uint64
    Team    string        // для будущей поправки на соперников
    stats.Counters
}

type Params struct { Alpha float64; Calibration int }  // α = 0.1, порог 10

// Build проходит матчи по порядку и возвращает состояние каждого игрока
func Build(rows []MatchRow, p Params) *Book
```

`Book` хранит по игроку список шагов: матч, сессия, R̄ до и после, число матчей до и после. Из него читаются:

- `OVR(id)` — R̄ после последнего матча, число матчей, признак калибровки;
- `Before(id, matchID)` — R̄ перед матчем;
- `Session(id, sessionID)` — R̄ перед первым матчем игрока в сессии и после последнего;
- `Last(id, n)` — сумма счётчиков последних n матчей (среднее за 20).

Шаг EMA по roadmap:

```
w  = max(R / сумма раундов игрока с этим матчем, 1 − (1 − α)^(R/24))
R̄ ← R̄ + w·(r_m − R̄)       (первый матч: R̄ = r_m)
```

Строки группируются по матчу, чтобы шаг знал состав (союзники и соперники) — задел под γ из 1.3, сейчас не используется.

Почему отдельный пакет, а не `internal/stats`: `stats` считает один матч из событий, а рейтинг — функция от упорядоченного набора матчей. 1.2–1.4 будут импортировать именно `rating`.

### 4. Данные из `internal/store`

`Store.RatingRows(ctx) ([]rating.MatchRow, error)` — один запрос: `match_players` × `matches` × `sessions`, `WHERE m.has_result = 1`, `ORDER BY s.date, s.id, m.ordinal, m.id`. Store возвращает сразу `[]rating.MatchRow`: `rating` зависит только от `stats`, циклов нет, а отдельный тип строки в store дал бы лишнее перекладывание.

Фильтры не применяются: OVR всегда по всем матчам (спека «Порядок матчей для рейтинга»).

### 5. API

Расчёт — `s.ratingBook(ctx)` (`internal/api/rating.go`): `RatingRows` + `rating.Build` на каждый запрос, где нужен рейтинг. Для сотен матчей это миллисекунды, кэш не нужен (пересчёт и перестановка сразу видны).

Новые поля (баллы — целые, `null`/отсутствие — «нет данных»):

```ts
type OVR = { score: number; rating: number; matches: number; calibrating: boolean; calibrationMatches: number }

PlayerView                 + score?: number           // оценка за матч / сессию / период; нет без раундов
GET /api/players           players[].ovr?: OVR
GET /api/players/{id}      ovr?: OVR; last20?: number; lastSession?: SessionChange
                           sessions[].change: SessionChange       // «к обычному» в разбивке
                           matches[].before?, matches[].vsUsual?  // как в scoreboard
GET /api/sessions/{id}     players[].change: SessionChange
GET /api/matches/{id}      players[].before?: number   // OVR перед матчем; нет — первый матч
                           players[].vsUsual?: number  // оценка матча − before
                           teams: { A?: TeamOVR; B?: TeamOVR }

type TeamOVR = { score: number; rated: number; total: number }  // «по rated из total»

type SessionChange = {
  sessionId: number
  score: number            // оценка за сессию (для подсказки в профиле)
  before?: number          // OVR перед первым матчем игрока в сессии; нет — первая сессия
  after: number            // OVR после последнего матча в сессии
  delta?: number           // after − before по округлённым значениям
  vsUsual?: number         // score − before
  matches: number          // матчей игрока после сессии (счётчик «8/10» в калибровке)
  calibrating: boolean     // OVR после сессии ещё в калибровке
  calibrationMatches: number // порог калибровки для счётчика «8/10»
}
```

`score` добавляется в `newPlayerView`, поэтому появляется во всех таблицах (в том числе разбивках профиля), без отдельной логики. `delta` и `vsUsual` считаются по округлённым баллам, чтобы «65 → 67, +2» всегда сходилось с показанными числами.

`rating` в `OVR` — R̄ до шкалы: понадобится для подбора составов (1.4), где силы сравниваются по R̄. Средний OVR команды так же считается по R̄ игроков перед матчем и только потом переводится в баллы (`Book.Before` для каждого игрока команды); игроки без матчей до этого не входят, `teams.X` нет, если таких нет ни одного.

Альтернатива — отдельный `GET /api/players/{id}/rating`, как у дуэлей. Отклонена: значения нужны в уже загружаемых таблицах, отдельный запрос добавил бы второй запрос на каждую страницу. Для истории (1.2) отдельный метод будет.

### 6. Конфигурация

`config.Config.RatingCalibration int` из `RATING_CALIBRATION_MATCHES`, по умолчанию 10, целое ≥ 1, иначе ошибка запуска «RATING_CALIBRATION_MATCHES: ожидается целое число не меньше 1». Передаётся в `api.Server.Rating rating.Params`. α — константа `rating.DefaultAlpha = 0.1` до 1.3.

### 7. Пороги шкалы метрик

Rating 2.0 у компании в среднем выше 1.0 (1.084), и при старых порогах `[0.85, 1.15]` «хорошо» получали 44% матчей, «плохо» — 28%. Пороги rating сдвинуты на **`[0.95, 1.25]`**: та же ширина ±0.15 вокруг медианы, по 34% матчей в «плохо» и «хорошо». Пороги K/D не меняются. Поправлены `web/src/metrics.ts`, README и требование «Шкала показателей» (дельта `specs/web-ui`).

### 8. Интерфейс по макетам

**Токены и ступени.** В `@theme` (`web/src/index.css`) — `--color-ovr-1…5` из доски «16 Оценка и OVR» (`#7F8794`, `#A2A9B5`, `#CDD2DA`, `#F2F4F7`, `#FFFFFF`). Цвета берутся через `var()` в стилях компонента, поэтому объявляются в `@theme static` (как шкала дуэлей). Ступень — функция `scoreTier(score)` в `web/src/metrics.ts`: 0–49, 50–64, 65–74, 75–89, 90+. Сравнение «к обычному» использует существующие `metric-good`/`metric-bad` и нейтральный цвет бейджа.

**Новые компоненты — `web/src/components/ui/Rating.tsx`:**

| Компонент | Что показывает | Где |
|---|---|---|
| `ScoreBadge` | плашка оценки/OVR: ступень, размер `sm` 22 px / `lg` 32 px / `xl` 50 px, калибровка (пунктир без заливки, приглушённый текст), у 90+ заливка | все экраны |
| `VsUsual` | иконка тренда (лучше / хуже / как обычно) или прочерк с причиной; вариант с числом (`+8`, `−5`, `±0`) для колонки «К обычному»; подсказка «Лучше обычного на 8 · обычно 74» | матч, профиль, сессия |
| `OvrChange` | «было → стало» и дельта в нейтральной рамке; компактный вариант «стало + дельта» для 390 px; метка «калибровка» в первой сессии; счётчик «N/10» в калибровке | сессия, профиль |
| `OvrTooltip` | подсказка у изменения: OVR за сессию, оценка за сессию с иконкой, «Обычно — OVR перед сессией», блок «Из чего сложилось» с заглушкой (наполнит change разложения) | профиль |
| `ScoreWithUsual`, `Delta`, `CalibrationCount`, `CalibrationTag`, `RatingTile`, `TeamOvr` | оценка с иконкой для колонок «Оценка»; дельта в рамке; «5/10»; метка «калибровка»; плитка профиля; средний OVR команды с «по N из M» | все экраны |

Подсказки — `title` для простых. `OvrTooltip` раскрывается по наведению и фокусу (кнопка), поэтому только в плитке профиля: ячейки таблиц обрезают содержимое, там изменение OVR поясняет `title`. Порог калибровки для «5/10» приходит из API (`calibrationMatches`). Тексты подсказок (`vsUsualText`, `ovrChangeText`, `scoreTierName`) — в `web/src/metrics.ts`.

**Экраны:**

- **Игроки.** Колонка OVR сразу за ником в `PLAYER_TOTAL_COLUMNS` (только на странице игроков), сортировка `sort=ovr`; ячейка — счётчик «N/10» при калибровке + `ScoreBadge sm`. На 390 px колонка видна без прокрутки, потому что стоит второй, сразу за закреплённым ником, — двойное закрепление не нужно. Подпись под таблицей: «OVR — общий уровень по всем матчам игрока, от периода не зависит; Rating — за выбранный период…».
- **Профиль.** Три плитки над `KpiGrid`: OVR (`ScoreBadge xl` + бейдж «Калибровка · N из 10 матчей»), «Среднее за 20» (`lg`), «Последняя сессия» (`OvrChange` с `OvrTooltip`, ссылка на сессию; в первой сессии — метка «калибровка»). На 390 px OVR на всю ширину, две плитки под ней. Колонка «Оценка» (`VsUsual` иконкой + `ScoreBadge sm`) в «По сессиям» и «Матчи»; в «По картам» её нет.
- **Сессия.** Третье значение сегмента вида итогов: `totals=scores` («Оценки»), «Основное» по-прежнему без параметра. Таблица: игрок, М, Rating, оценка, «К обычному» (`VsUsual` с числом), «OVR за вечер» (`OvrChange`). На 390 px — игрок, оценка, иконка сравнения, `OvrChange` компактный; М и Rating скрыты. `StatTable` не умеет прятать колонки стилями без сдвига ширин (`table-fixed`), поэтому вид берёт другой набор колонок по хуку `useNarrow` (`web/src/media.ts`, тот же брейкпоинт 720 px).
- **Матч.** Колонка «Оценка» перед Rating в `PLAYER_MATCH_COLUMNS`, `VsUsual` иконкой слева от `ScoreBadge`. В счёте у названия команды — `ScoreBadge` среднего OVR и пометка «по N из M» (как бейдж покрытия), пояснение в подсказке. Подробный вид матча колонку Rating не показывает, поэтому оценки там нет; колонка добавлена в таблицы команд, общие для S07 и S17. Если у всех игроков команды первый матч, вместо среднего — «—» с подсказкой.

Подписи «HLTV Rating 1.0» → «HLTV Rating 2.0» в заголовках колонок и плитке профиля.

## Risks / Trade-offs

- [Rating 2.0 восстановлен, а не официальный] → в подписи и README указано «восстановленная формула», сверка коэффициентов с awpy — тест на пример из спеки.
- [Пересчёт всех матчей на каждый запрос] → при росте до тысяч матчей замерить; кэш с инвалидацией по изменению матчей — отдельный change (в roadmap — этап 2.5).
- [Константы шкалы подобраны на малом числе матчей] → подбираются один раз и фиксируются; уточнение — только вместе с 1.3, с явным предупреждением, что съедет история.
- [Игрок зашёл посреди матча, его счётчики делятся на все раунды] → известное ограничение, рейтинг такого матча занижен; не исправляем.
- [Rating 2.0 меняет числа в уже знакомых таблицах] → ожидаемо по решению пользователя; README объясняет смену формулы.

## Migration Plan

Миграции БД нет. После деплоя все значения rating сразу считаются по 2.0. Откат — откат кода.
