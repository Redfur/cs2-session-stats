# Дорожная карта: рейтинг игроков, подбор составов, группы

Файл хранит контекст обсуждения (октябрь 2026), чтобы по нему составлять отдельные OpenSpec changes.
Это не спецификация: требования появляются в `openspec/specs/` только через change.
Каждый пункт ниже — кандидат в отдельный change (`/opsx:propose <имя>`). Когда change создан или заархивирован, отметить это в таблице статусов.
Если при обсуждении change решение меняется, поправить и этот файл.

## Цель

Оценить каждого игрока компании, чтобы делить на равные команды в будущих матчах:

- рейтинг по шкале 0–100 (как в карточках FIFA);
- оценка за отдельный матч (карту) и за сессию;
- общий уровень по последним матчам и сравнение «сыграл лучше или хуже обычного»;
- изменение рейтинга за сессию («было 65, стало 67») и история на графике, как у FACEIT;
- в профиле — роль игрока и карточка с наглядными характеристиками;
- в перспективе — сервис: вход через Steam, у каждой компании друзей своя группа и свой рейтинг.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Какой рейтинг брать за основу | Восстановленная формула HLTV Rating 2.0. Формулы 2.1 и 3.0 закрыты, повторить их честно нельзя (см. «Справка»). |
| Шкала | 0–100, **одна формула для всех групп**. Растягивать шкалу под группу не будем. |
| Общий уровень игрока (OVR) | Экспоненциальное скользящее среднее (EMA), а не окно из N матчей. «Среднее за последние 20» — отдельный показатель. |
| Один общий change на всё | Нет. Каждое улучшение — отдельный небольшой change (принцип из `CLAUDE.md`). |
| Порядок | Сначала рейтинг в текущем режиме (одна компания), потом сервис. Рейтинг не ждёт авторизации. |
| Рейтинг в многопользовательском сервисе | Отдельный рейтинг в каждой группе. Глобального рейтинга нет. |
| Вступление в группу | Только через приглашение и согласие пользователя. Приглашения бывают автоматические (каждому, кто играл в матчах группы, если это включено в настройках группы) и от владельца (адресно — в раздел «Уведомления» пользователя — или ссылкой). Без согласия в группу не зачисляют. См. 2.3. |
| Автоприглашения | Настройка группы, выбирается при создании: отправлять ли приглашения автоматически всем игрокам, найденным в демках. Запрета для отдельного игрока нет. |
| Передумать после отклонения | Нельзя самому. Только если владелец пришлёт приглашение заново. |
| Запрос доступа в группу | Возможно, стоит предусмотреть (2.6). |
| Скрыть свою статистику в чужой группе | Нельзя. Отклонивший приглашение просто не видит эту группу; его статистику по-прежнему видят участники группы. |
| Кто загружает демки и отбирает матчи группы | Только владелец группы. |
| Кто видит рейтинг группы | Только участники группы (включая владельца). Если два пользователя состоят в двух общих группах, каждый видит рейтинг другого в обеих. |
| Админ | Под «админом» имеется в виду владелец группы. Администратора всего сервиса и админки пока нет, это возможная идея на будущее. |
| Профиль игрока | Роль и карточка с наглядными характеристиками. Стандартный набор характеристик (одинаковый у всех, для сравнения) и «сильные стороны» (только то, в чём игрок хорош) — **разные блоки**. |

| Порог калибровки | 10 матчей. Настраивается переменной окружения; после 2.2 владелец группы может переопределить для своей группы; позже — в админке сервиса. |
| Период карточки и роли | Как у OVR: экспоненциальное затухание, последние матчи весят больше всего, старые — меньше. |

## Общие принципы

- **Источник истины — сырые счётчики**: `match_players` (`stats.Counters`) и расширенные таблицы `add-extended-demo-stats` (`match_player_ext`, `match_player_weapons`, `match_clutches`, `match_kills`, `match_rounds`), как сейчас. Рейтинг, OVR, оценки и история считаются при чтении и в БД не хранятся (до этапа 2.5, см. там). Смена формулы или констант пересчитывает всю историю сама, без `ProcessingVersion`.
- **Рейтинг — функция от упорядоченного набора матчей.** Сейчас набор — все матчи с `has_result = 1`. После этапа 2.2 — включённые матчи группы. Формулы при этом не меняются.
- **Порядок матчей:** `sessions.date`, затем `sessions.id` (порядок создания сессий с одной датой), затем `matches.ordinal`. Перестановка, удаление и пересчёт матча автоматически меняют историю.
- **Шаг обновления знает состав матча** (союзники и соперники), чтобы позже включить поправку на силу соперников без смены модели (см. 1.3).
- **Внутри закрытой группы рейтинг сам получается относительным.** В 5×5 между своими каждое убийство одного — смерть другого: в среднем по группе убийств за раунд столько же, сколько смертей, урон нанесённый примерно равен полученному. Средний игрок любой группы получает примерно одинаковый рейтинг. Поэтому одна формула шкалы даёт числа, которые зависят от группы: 85 значит «сильно лучше своей компании», а не «силён вообще».

## Этап 1. Рейтинг в текущем режиме (одна компания)

### 1.1 `add-player-rating` — рейтинг, оценки, OVR

**Rating 2.0 (восстановленная формула).** Коэффициенты сверены по исходникам awpy (`awpy/stats/rating.py`):

```
KPR = Kills/Rounds, DPR = Deaths/Rounds, APR = Assists/Rounds
KAST — в процентах (0–100), ADR — урон за раунд
Impact   = 2.13·KPR + 0.42·APR − 0.41
Rating20 = 0.0073·KAST + 0.3591·KPR − 0.5329·DPR + 0.2372·Impact + 0.0032·ADR + 0.1587
```

- Все входные данные уже есть в `stats.Counters`. Это новая функция рядом с `Counters.Rating()` (HLTV 1.0), `ProcessingVersion` не поднимается.
- Формула линейна по величинам «на раунд»: Rating20 по сумме счётчиков нескольких матчей равен среднему Rating20 матчей, взвешенному по раундам. Так же, как у 1.0, итоги сессии и любого периода — это Rating20 от суммы счётчиков.
- Многокиллы, открывающие дуэли и клатчи в восстановленной формуле не участвуют, это известное упрощение.
- **Rating 2.0 заменяет 1.0 во всех таблицах** (решение пользователя): сессия, матч, игроки, профиль, разбивки. Что поправить в change:
  - пороги `rating` в `web/src/metrics.ts` (`[0.85, 1.15]`) и спеку шкалы метрик — подобрать по распределению Rating 2.0 на данных компании;
  - спеки `player-stats`, `match-stats`, `web-ui` и тексты (подписи «Rating» → «Rating 2.0» там, где нужно);
  - инвариант «Rating — HLTV 1.0» в `CLAUDE.md` и README;
  - `Counters.Rating()` (1.0) убрать или оставить для сравнения в 1.3 — решить в design.

**Шкала 0–100.** Плавная S-образная функция от Rating20 (логистическая), одна для всех. Предварительно:

```
score(r) = 100 / (1 + exp(−k·(r − r0))),  k = 4, r0 ≈ 0.899  (так что 1.00 → 60)
```

| Rating20 | 0.50 | 0.70 | 0.85 | 1.00 | 1.15 | 1.30 | 1.50 | 1.80 |
|---|---|---|---|---|---|---|---|---|
| Баллы | 17 | 31 | 45 | 60 | 73 | 83 | 92 | 97 |

- **Выбрано в `add-player-rating` (2026-10-14): `k = 3`, `r0 = 0.95`** — средний Rating 2.0 компании 1.084 даёт 60, постоянные игроки 38–80. Пороги шкалы метрик для rating — `[0.95, 1.25]`.
- Константы `k` и `r0` подобрать один раз по накопленным матчам (средний Rating20 среди друзей может быть не ровно 1.0), чтобы постоянные игроки укладывались примерно в 40–90, а 100 было практически недостижимо. После этого константы не трогать, иначе съедет вся история.
- Баллы округляются до целых при выводе. Шкала нелинейна, поэтому средние всегда считаются по Rating20 и только потом переводятся в баллы, а не усредняются сами баллы.

**Оценка за матч и за сессию.** `score(Rating20(счётчики))`: за матч — по счётчикам матча, за сессию — по сумме счётчиков игрока за матчи сессии.

**OVR — EMA рейтинга по матчам.** Rating20 линеен, поэтому EMA рейтинга матчей равна рейтингу от EMA компонентов. Хранить компоненты отдельно не нужно.

```
до первого матча: R̄ не определён
после матча с R раундами и рейтингом r_m:
  w  = max(R / сумма_раундов_игрока_с_учётом_этого_матча,  1 − (1 − α)^(R/24))
  R̄ ← R̄ + w·(r_m − R̄)          (первый матч: R̄ = r_m)
OVR = score(R̄)
```

- `α ≈ 0.1` (память примерно как у окна в 20 матчей: последние 20 дают около 88% веса). Подобрать в 1.3.
- `R/24` взвешивает по длине: матч 13:3 весит меньше, чем 16:14 с овертаймом. При α = 0.1 матч на 16 раундов даёт вес 0.068, на 24 — 0.1, на 30 — 0.123.
- Первая часть `max` даёт обычное взвешенное среднее, пока матчей мало (примерно первые 10). Это заодно и калибровка новичков.
- **Калибровка:** пока у игрока меньше **10 матчей**, OVR показывается с меткой «калибровка» и не участвует в подборе составов как надёжное значение. Порог задаётся переменной окружения (например, `RATING_CALIBRATION_MATCHES`, по умолчанию 10) в `internal/config`. После 2.2 владелец группы может переопределить его для своей группы (`groups.calibration_matches`, NULL — значение из окружения). Если появится админка сервиса, значение по умолчанию переедет туда. При пороге 10 и α = 0.1 калибровка совпадает с участком, где EMA ещё равна обычному среднему.
- Почему EMA, а не окно: в окне OVR меняется и от выпавшего старого матча. Можно сыграть лучше обычного и всё равно потерять рейтинг, потому что выпал ещё более удачный матч. У EMA каждое изменение объясняется только новыми играми.

**«Среднее за последние 20».** `score(Rating20(сумма счётчиков последних 20 матчей игрока))` — отдельный буквальный показатель в профиле.

**Сравнения:**

- **Лучше или хуже обычного:** оценка за матч или сессию против OVR **до** этого матча или сессии. С OVR после сравнивать нельзя: сессия будет сравниваться сама с собой.
- **Изменение за сессию:** OVR после последнего матча игрока в сессии минус OVR перед первым её матчем («65 → 67, +2»). Если игрок не играл в сессии, изменения нет. Если сессия у него первая, показываем «калибровка», а не изменение.

**Где показывать (уточнить по макетам Claude Design):**

- Список игроков: колонка OVR, метка калибровки.
- Профиль: OVR, «среднее за 20», изменение за последнюю сессию.
- Итоги сессии: оценка за сессию, изменение OVR за сессию, «лучше или хуже обычного».
- Scoreboard матча: оценка за матч.

**Почему изменился рейтинг (предложение).** Rating20 линеен, поэтому изменение R̄ за сессию точно раскладывается по слагаемым формулы: «+3 = убийства +2.1, урон +1.4, смерти −0.5, KAST 0». Показывать подсказкой у изменения OVR, чтобы снять вопрос «за что мне минус». Баллы шкалы нелинейны, поэтому вклады считаются в R̄ и пропорционально переводятся в баллы изменения.

**API (набросок):** поля в существующих ответах (`PlayerView`, итоги сессии, игроки матча) или отдельный `GET /api/players/{steamId}/rating`. Решить на этапе design, по образцу дуэлей.

**Пограничные случаи:**

- Игрок зашёл или вышел посреди матча: его счётчики делятся на все раунды матча (известное ограничение ADR). Рейтинг такого матча занижен.
- Ничья не влияет: рейтинг не зависит от результата.
- Расчёт при чтении: для одной компании это сотни матчей, один проход по матчам в порядке времени — дёшево. Кэш не нужен.

### 1.3 `add-rating-evaluation` — проверка на прошлых матчах

Цель — проверять рейтинг на прошлых матчах, а не подбирать формулу на глаз.

- Для каждого матча с результатом (кроме ничьих) берём OVR игроков **перед** этим матчем (только по предыдущим матчам, без подглядывания) и предсказываем победителя по разнице средних OVR команд.
- Метрики: доля угаданных победителей, log loss или Brier score, сравнение с базовой линией 50%.
- Сравнить варианты: Rating 1.0 и 2.0, разные α, шкала окна против EMA, поправка на силу соперников (γ, см. ниже).
- Форма: CLI-команда `cs2stats rating-eval` (вывод таблицы), без UI.
- Матчей мало: подбирать только 1–2 параметра, иначе модель запомнит прошлое. Осмысленно примерно с 30 и более матчей.
- Результат: выбранные α, γ, константы шкалы `k`, `r0` и масштаб `s` для шанса победы в 1.4 записываются в design соответствующего change и в этот файл.

**Поправка на силу соперников (кандидат).** Заложить в шаг EMA с γ = 0 и включить, если проверка покажет пользу:

```
ожидание_i = R̄_i − γ·(средний R̄ соперников − средний R̄ союзников)
R̄_i      += w·(r_m − ожидание_i)
```

Против сильных ожидание ниже, против слабых выше. Внутри одной компании с перемешанными составами эффект, скорее всего, небольшой, но при 6–8 постоянных игроках составы повторяются, и поправка может помочь.

### 1.4 `add-team-balancer` — подбор составов

- Вход: список игроков на сессию (из известных игроков, после 2.2 — из участников группы). Обычно 10, допускается 8–12 (команды ⌊n/2⌋ и ⌈n/2⌉).
- Полный перебор разбиений: для 10 игроков C(10,5)/2 = 126 вариантов.
- Цель — минимальная разница сил команд. Силу сравнивать по среднему R̄ (рейтинг до шкалы), а не по сумме баллов: шкала нелинейна.
- Показывать 2–3 лучших варианта и шанс победы: `P(A) = σ((R̄_A − R̄_B)/s)`, где `s` берётся из 1.3. До 1.3 шанс не показывать.
- Ограничения (по желанию): «эти двое вместе» или «эти двое порознь», штраф за повтор составов прошлой сессии.
- Роли (после 1.6): не больше одного снайпера в команде, энтри поровну.
- Синергия пар (идея из 3.2): не складывать в одну команду пару с заметно повышенным процентом побед вместе.
- Игроки в калибровке и новички: средний R̄ компании или оценка вручную.
- Ничего не хранится, результат — экран, который можно скопировать или показать. Возможное развитие: сохранить план и сравнить с фактическими составами.
- Где в UI: отдельная страница или кнопка в сессии. Решить по макету.

### 1.5 `add-player-card` — карточка игрока

Два раздельных блока на вкладке «Обзор» профиля (по решению пользователя):

1. **Характеристики** — стандартный набор, одинаковый у всех игроков, чтобы сравнивать. Как атрибуты в карточке FIFA.
2. **Сильные стороны** — только то, в чём игрок заметно лучше своей компании (0–3 значка). Если таких нет, блок не показывается.

**Характеристики (черновой набор, 6 штук, 0–100):**

| Характеристика | Из чего считается | Таблицы |
|---|---|---|
| Огневая мощь | убийства за раунд, ADR, доля раундов с 2+ убийствами | `match_players` |
| Вход | открывающие убийства за раунд, доля выигранных открывающих дуэлей `OK/(OK+OD)` | `match_players` |
| Выживание | доля раундов, где выжил; среднее время жизни | `match_player_ext` |
| Командность | KAST, убийства в размен за раунд, доля разменянных смертей, ассисты за раунд | `match_players`, `match_player_ext` |
| Клатч | доля выигранных клатчей с весом по числу противников (1v1 = 1, 1v2 = 2…) | `match_clutches` |
| Гранаты | урон HE и огнём за раунд, флеш-ассисты и ослеплённые противники за раунд | `match_player_ext` |

Кандидат на седьмую — «Точность» (HS%, попадания / выстрелы по `match_player_weapons`). Решить по макету: 6 характеристик читаются лучше.

**Как считать баллы:**

- Каждый показатель делится на опорное среднее (константа, подобранная один раз по накопленным данным, как `k` и `r0` у OVR), показатели характеристики усредняются с весами, результат проходит через ту же S-образную шкалу: среднее → 60. Одна формула для всех групп, как у OVR.
- **Мало событий** (клатчи, открывающие дуэли): сглаживание к среднему — к фактическим попыткам добавляется несколько «виртуальных» попыток со средним результатом. Иначе 1 из 1 клатча даёт 100.
- **Период — как у OVR** (решение пользователя): все матчи игрока с экспоненциальным затуханием. Каждый показатель — отношение затухающих сумм: `Σ wⱼ·числительⱼ / Σ wⱼ·знаменательⱼ`, где вес матча `wⱼ = (1 − α)^(раундов в более поздних матчах / 24)`, α — та же, что у OVR. Так последние матчи весят больше, а сглаживание к среднему работает на «эффективном» числе событий. Фильтр периода профиля на карточку не влияет.
- Характеристики показываются после калибровки (тот же порог, 10 матчей), до этого — «мало данных».
- Матчи без событий урона или ослеплений (`has_damage_events`, `has_flash_events`) не входят в соответствующие характеристики.
- Зависит от 1.1 (шкала `score`). Хранить ничего не нужно.

**Сильные стороны (значки):**

- Характеристика заметно выше среднего по компании (например, на 1σ или первое–второе место среди постоянных игроков).
- Плюс отдельные узкие черты, которых нет в характеристиках: «Хедшотер» (HS%), «Прострел» (доля убийств через стену), «Дальнобой» (средняя дистанция убийства), «Через дым», «Дефьюзер» (доля обезвреживаний).
- Пороги — относительно компании, поэтому после 2.2 считаются по группе.
- Значки — не награды: значок описывает устойчивый стиль за период, награда — событие (см. 3.1).

**Карточка для обмена:** выгрузка картинкой (OVR, роль, характеристики) для чата — отдельным шагом, если понадобится.

### 1.6 `add-player-role` — роль игрока

Роль описывает **стиль**, а не уровень: «энтри» может быть и сильным, и слабым. Одна основная роль, при явном перевесе — вторая.

| Роль | Признак | Данные |
|---|---|---|
| Снайпер | доля убийств с AWP ≥ 25–30% (порог подобрать) | `match_player_weapons` |
| Энтри | открывающих дуэлей (OK+OD) за раунд заметно больше среднего по компании — важна частота, а не успех | `match_players` |
| Саппорт | много ослеплённых противников, флеш-ассистов и смоков за раунд при малом числе открывающих дуэлей | `match_player_ext` |
| Люркер | на T-стороне поздние убийства в раунде, долгое время жизни, мало открывающих дуэлей. **Проверить на демках**: без позиций игроков признак может не работать, тогда роль убрать | `match_kills`, `match_rounds`, `match_player_ext` |
| Стрелок | по умолчанию, если ни один признак не выражен | — |

- Признаки — относительно компании (z-оценка по постоянным игрокам), кроме доли AWP (абсолютный порог).
- Минимум данных — порог калибровки (10 матчей), иначе «роль не определена».
- Период — как у карточки: затухающие суммы, последние матчи весят больше всего.
- Роль по сторонам (T/CT): данные по сторонам есть только для выживания, для остального понадобится сторона в `match_kills` (через `match_rounds.side_a`). Позже, если будет нужно.
- Использование: значок роли в шапке профиля и в списке игроков, учёт ролей в подборе составов (1.4).
- Проверка: на реальных данных компании роли должны совпадать с тем, как друзья сами себя описывают. Пороги подбирать под это, а не на глаз.

## Этап 2. Многопользовательский сервис

### Модель

- **Пользователь** — человек, вошедший через Steam (SteamID64).
- **Группа** — компания друзей: название, владелец, сессии и матчи.
- **Участник группы (member)** — пользователь, принявший приглашение. Видит всё в группе.
- **Игрок группы (participant)** — SteamID, который встречается во включённых матчах группы. Регистрироваться не обязан. Список игроков группы вычисляется из матчей, а не хранится.
- Рейтинг, OVR, история, оценки и подбор составов считаются **только по включённым матчам группы**. У игрока столько рейтингов, во скольких группах он играет. Это ожидаемое поведение, а не ошибка.

### 2.1 `add-steam-auth` — вход через Steam

- **Steam OpenID 2.0** (`https://steamcommunity.com/openid/login`). После возврата обязательна проверка через `openid.mode=check_authentication`, SteamID64 берётся из `openid.claimed_id` (`https://steamcommunity.com/openid/id/<steamid64>`). Сверять `return_to` и `realm` с `PUBLIC_URL`.
- Ник и аватар: Steam Web API `GetPlayerSummaries` (нужен `STEAM_API_KEY`, необязательный). Без ключа — ник из последней демки.
- **Сессия входа:** случайный токен в cookie `HttpOnly; Secure; SameSite=Lax`, в БД хранится хэш токена (`auth_sessions`), срок жизни и продление. Выход удаляет запись.
- **CSRF:** `SameSite=Lax` и проверка `Origin` на изменяющих запросах.
- Все `/api/*`, кроме входа, требуют авторизации. CLI (`parse`, `reparse`) работает как раньше.
- **До групп (2.2):** доступ по списку из конфигурации `ALLOWED_STEAM_IDS`, чтобы сервис можно было открыть одной компании уже после 2.1.
- Новые таблицы: `users (steam_id PK, name, avatar_url, created_at, last_login_at)`, `auth_sessions (token_hash PK, steam_id, created_at, expires_at)`.
- Новый конфиг: `PUBLIC_URL`, `STEAM_API_KEY` (необязательный), `ALLOWED_STEAM_IDS`.
- Обновить инвариант «Авторизации нет» в `CLAUDE.md`.

### 2.2 `add-groups` — группы

- Таблицы: `groups (id, name, owner_steam_id, created_at)`, `group_members (group_id, steam_id, role: owner|member, joined_at)`.
- `sessions.group_id NOT NULL`. Миграция создаёт группу «Основная» и переносит в неё все существующие сессии. Владельца назначает сервис при старте из конфигурации (`ALLOWED_STEAM_IDS` или отдельный параметр), потому что миграция не читает окружение. Остальные из списка становятся участниками.
- **Флаг учёта матча:** `matches.counted` (по умолчанию 1). Исключённый матч виден в сессии с пометкой, но не входит в статистику, рейтинг и дуэли группы. Переключает только владелец. Подсказка владельцу: «в матче N игроков, которые раньше в группе не встречались».
- **Права:**
  - Читать данные группы (сессии, матчи, игроки, рейтинги, дуэли, история) могут только её участники.
  - Изменять (сессии, загрузка, импорт, порядок, удаление, пересчёт, учёт матчей, настройки группы) может только владелец.
  - Проверка на каждом endpoint: группа берётся из пути или из сессии и матча. Чужой id отвечает 404, а не 403, чтобы не раскрывать существование.
- **API и адреса:** `/api/groups`, `/api/groups/{gid}/sessions`, `/api/groups/{gid}/players/{steamId}`… Во фронте `/g/:gid/...`, переключатель групп в каркасе.
- **Профиль игрока между группами:** зритель видит рейтинг игрока во всех группах, где зритель — участник, а игрок встречается в матчах. На странице игрока переключатель «в группе A / в группе B». Общей цифры нет. Общую статистику без рейтинга (K/D, ADR по всем доступным матчам) можно добавить отдельно, если понадобится.
- **Первый вход:** сначала приглашения (2.3), если они есть. Нет ни групп, ни приглашений → экран «Создайте группу» (название) → первая сессия → загрузка демок → игроки появляются из демок.
- **Порог калибровки группы:** `groups.calibration_matches` (NULL — значение из окружения), меняет владелец.
- Выйти из группы может участник. Удалить участника, передать владение и удалить группу может владелец. Удаление группы удаляет её сессии и матчи; правила для общих матчей — после 2.4.
- **Ограничение до 2.4:** `matches.sha256 UNIQUE` глобально, поэтому одну и ту же демку нельзя загрузить в две группы. Ошибка: «этот матч уже загружен в другую группу» — без названия группы.

### 2.3 `add-group-invites` — приглашения и уведомления

В группу попадают только после согласия. Приглашения бывают трёх видов, все приходят в раздел «Уведомления».

**Раздел «Уведомления».**

- Отдельная страница и счётчик непрочитанного в шапке. При входе, если есть новые приглашения, пользователь сразу видит их.
- В 2.3 — только приглашения в группы. Позже сюда же: запросы доступа и ответы на них (2.6), награды (3.1), «демка скоро пропадёт» (3.2).
- Уведомлений вне сервиса нет: Steam OpenID не даёт контактов.

**1. Автоприглашения по участию в матчах.**

- Включаются настройкой группы `groups.auto_invite` — переключатель на экране создания группы, потом меняется в настройках. Значение по умолчанию решить в design (предложение: включено).
- Приглашение не хранится, а вычисляется: автоприглашения включены, пользователь — игрок группы (его SteamID есть во включённых матчах группы), не участник и не отклонял её.
- В уведомлении: название группы, владелец, сколько матчей сыграно вместе. Кнопки «Принять» и «Отклонить».
- Новые матчи с игроком создают приглашение при следующем входе, если он ещё не отвечал.
- Включение настройки позже действует на всех уже найденных игроков группы (приглашение вычисляемое).
- Запрета автоприглашения для отдельного игрока нет (решение пользователя). Если случайный человек попал в матч, владелец может исключить матч из учёта или выключить автоприглашения и приглашать вручную.

**2. Приглашение от владельца адресно.**

- Владелец в списке игроков группы нажимает «Пригласить» у игрока — приглашение приходит ему в «Уведомления». Можно пригласить и человека без матчей в группе по SteamID или ссылке на профиль Steam.
- Работает и для того, кто отклонил приглашение раньше: это единственный способ вернуть его (решение пользователя — сам передумать он не может).
- Незарегистрированный пользователь увидит приглашение при первом входе.

**3. Приглашение ссылкой.**

- Для случаев, когда SteamID неизвестен. Ссылка вида `/invite/<token>`: вход через Steam → «Вступить в группу X?» → участник.
- Срок действия, лимит использований, отзыв. Создаёт только владелец.

**Ответ на приглашение.**

- **Принять** → запись в `group_members`, группа появляется в списке групп пользователя.
- **Отклонить** → запись в `group_declines (group_id, steam_id, declined_at)`. Группа пользователю не показывается, свою статистику в ней он не видит, автоприглашения от неё больше не приходят. Списка «Отклонённые» нет. Новое приглашение от владельца (адресное или ссылкой) снимает отклонение, повторный отказ снова скрывает группу.
- Скрыть свою статистику в группе нельзя (решение пользователя): участники видят его как игрока своих матчей, даже если он отклонил приглашение или не зарегистрирован.

**Хранение (набросок).**

- `group_invites (id, group_id, steam_id NULL, token_hash NULL, created_by, created_at, expires_at, max_uses, uses, status: pending|accepted|declined|revoked)`: адресное — с `steam_id`, ссылка — с `token_hash`.
- `group_declines (group_id, steam_id, declined_at)`.
- `groups.auto_invite`.
- Отметка о прочтении уведомлений: `notification_reads` или поле `seen_at` у приглашений — решить в design.

### 2.4 `add-shared-matches` — один матч в нескольких группах

- Разделить «разобранную демку» и «матч в сессии группы»:
  - разобранная демка — глобальная: sha256, источник на платформе, результат разбора, `match_players`, дуэли, версии;
  - связь `session_matches (session_id, match_id, ordinal, counted)` — в группе.
- Загрузка демки, которая уже есть (тот же sha256 или тот же источник `source_platform` + `source_number` + `map_number`), в другую группу создаёт связь без повторного скачивания и разбора.
- Удаление из группы удаляет связь. Демка удаляется, когда на неё не осталось связей.
- Пересчёт (`reparse`) — глобальный, на все группы.
- Загрузки по ссылке (`imports`) остаются в группе.
- Утечки нет: подключить чужой матч можно, только имея тот же файл или ссылку, то есть будучи в этом матче или имея его демку.

### 2.5 Публичный деплой

- Хранилище демок: S3 или MinIO через `ingest.Storage`, политика хранения (удаление после разбора или срок).
- Лимиты на пользователя: объём загрузок в день, число групп, размер демки (`MAX_DEMO_SIZE` уже есть).
- HTTPS через reverse proxy, резервные копии SQLite (например, Litestream). Переход на Postgres — только если упрёмся.
- Если групп и матчей станет много: хранить значения R̄ после каждого матча (материализованная история по группе) и пересчитывать фоновой задачей при смене формулы. Счётчики остаются источником истины.
- Позже: администратор сервиса и админка.

### 2.6 `add-group-access-requests` — запрос доступа (возможно)

Обратный путь к приглашению: пользователь просит доступ, владелец решает.

- **Как найти группу.** Чужие группы пользователю не видны. Варианты:
  - ссылка на группу от владельца или участника (`/g/<публичный код>` → «Запросить доступ»), не дающая доступа сама по себе, в отличие от `/invite/<token>`;
  - если автоприглашения выключены, игроку группы показывать «Вас нашли в группе X — запросить доступ»? Это раскрывает существование группы, которую владелец не хотел приглашать. Скорее нет.
- **Поток:** «Запросить доступ» (необязательный комментарий) → уведомление владельцу с кнопками «Принять» и «Отклонить» → ответ приходит пользователю в «Уведомления».
- **Ограничения от спама:** один открытый запрос на группу, после отказа повторить можно не раньше чем через N дней (или никогда — решить).
- **Отклонившие приглашение** могут запросить доступ. Это не противоречит правилу «сам передумать не может»: решает владелец.
- Хранение: `group_access_requests (id, group_id, steam_id, comment, created_at, status, decided_at)`.

## Этап 3. Идеи на потом

### 3.1 Награды и серии (nice to have)

Решение пользователя: нужно отдельно продумать, какие награды бывают. Пока это черновой список для обсуждения.

**Принципы:**

- Награда — **событие** (сделал в матче, сессии или за серию). Значок сильной стороны (1.5) — устойчивый стиль. Не смешивать.
- Считается при чтении из уже сохранённых данных, ничего не хранится.
- После 2.2 — в пределах группы: «лучший в компании», «первый раз в компании».
- Шуточные анти-награды могут обижать: по умолчанию выключены или отдельной настройкой группы.

**Кандидаты:**

| Тип | Примеры | Данные |
|---|---|---|
| За матч | эйс; клатч 1v3 и больше; 4+ открывающих убийства; убийство ножом, HE, через стену, без прицела; 5+ флеш-ассистов | `match_players`, `match_clutches`, `match_kills` |
| За сессию | лучший игрок вечера (по оценке за сессию); самый большой рост OVR; лучший матч вечера | 1.1 |
| Серии | 3 сессии подряд выше обычного; 5 матчей подряд с KAST ≥ 70%; серия побед | 1.1, `match_players` |
| Вехи | 100 / 500 / 1000 убийств; 100 клатчей; первый раз OVR 80+ | суммы счётчиков, 1.1 |
| Анти-награды | больше всех открывающих смертей; «ослепил своих»; смерть первым в N раундах подряд | `match_players`, `match_kills` |

Где показывать: в итогах сессии (награды вечера), в профиле (полка наград), в итогах вечера для чата (см. ниже).

### 3.2 Остальные идеи (не обсуждены)

**Рейтинг:**

- **Фильтр качества матчей (nice to have, решение пользователя: пока ценности не видно).** Матч не входит в OVR и историю (но остаётся в таблицах), если:
  - в демке нет событий урона (`matches.has_damage_events = 0`, старые бета-демки: ADR = 0 занижает рейтинг);
  - запись не с начала матча (`first_round > 1`);
  - меньше 8 игроков или неравные составы (ботов парсер в игроки не берёт: `pl.IsBot || SteamID64 == 0`);
  - матч прерван рано (меньше 10 раундов, порог уточнить).

  Причину исключения показывать у матча. Восстановленный последний раунд (`restored_round`) на базовые счётчики не влияет.
- **Точность рейтинга («65 ± 4»)** — по разбросу оценок за матчи и их числу. Можно использовать вместо жёсткого порога калибровки, как риск в подборе составов и как метку «давно не играл».
- **Склейка аккаунтов** — владелец связывает несколько SteamID в одного человека (второй аккаунт друга). До 2.2 — таблица соответствий, после — настройка группы.
- **Модель Брэдли — Терри по личным дуэлям** (`match_duels` уже есть): P(A убьёт B) = σ(s_A − s_B). Сила с поправкой на соперника по каждой паре. Сравнить с EMA в 1.3.
- **Учёт результата матча** (TrueSkill или Glicko по победам команд) как добавка к рейтингу по статистике. Ловит вклад, которого нет в цифрах (связь с командой). Нужно много матчей.
- **Свой рейтинг «по мотивам» 2.1:** размены, клатчи и урон гранатами в формуле. Данные теперь есть (`add-extended-demo-stats`), веса проверяются через 1.3.
- **По мотивам 3.0:**
  - поправка на экономику: нужна стоимость снаряжения в дуэли, парсер её пока не собирает;
  - Round Swing: вклад в шанс выиграть раунд. Модель шанса по числу живых с каждой стороны и по поставленной бомбе строится по своим же демкам (`match_kills`, `match_rounds`).
- **Рейтинг по картам:** OVR по матчам одной карты (Mirage, Inferno…), при достаточном числе матчей.
- **Сезоны:** итоги квартала или полугода. EMA не сбрасывается, это только срезы истории.

**Подбор составов:**

- **Синергия пар:** процент побед и средняя оценка, когда двое в одной команде, против того же порознь. Данные есть (`match_players.team`, `result`), показывать с порогом по числу совместных матчей.
- **Ротация на вечер:** план на 3–4 карты, каждый раз примерно поровну, но составы разные. При 9 или 11 игроках — очередь, кто пропускает карту.
- **Проверка прогноза после сессии:** «подбор обещал 55/45, итог 13:11». Требует хранить выбранный план (отход от «ничего не хранится» в 1.4).

**Сессии и сервис:**

- **Итоги вечера для чата:** короткий текст (лучший игрок, рост, лучший матч, награды). Сначала кнопка «скопировать», в сервисе — бот или webhook группы в Telegram или Discord.
- **Напоминание об истечении демок FastCup:** срок приходит в ответе (`replayExpirationDate` уже читается в `internal/importer/platforms.go`, но не сохраняется). Предупреждать о загрузках, которые скоро пропадут.
- **Автоимпорт с FastCup (исследовать):** если в GraphQL FastCup есть список матчей игрока, сервис мог бы находить кастомки, где играло 8 и больше участников группы, и предлагать владельцу добавить их. Hasura пропускает только запросы из allowlist, поэтому сначала проверить, есть ли такой запрос на странице профиля.
- **Выгрузка данных группы** (CSV или JSON).

## Справка: версии рейтинга HLTV

- **1.0** — открытая формула (KPR, выживаемость, многокиллы). Сейчас в проекте: `stats.Counters.Rating()`.
- **2.0** — добавлены KAST и ADR. Официальной формулы нет, есть восстановленная сообществом (см. 1.1). Её же использует awpy.
